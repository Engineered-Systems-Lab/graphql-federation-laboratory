## Meaningful transition

The fourth step of the data scale-up moved the whole federation layer from the small data to the large data. The expected outcomes were derived first, by `federation/acceptance/derive_expected.py` from the released files and not from a run: Missions release 1.1 read in the contract's order, mapping release 1.2 (the assets and the 800 crew references), the Assets dataset 1.1 and the 1,000 people of `personnel-v2-large-004`. Question 6 on the large data is mixed: 182 missions confirmed with a senior officer, 65 confirmed without, 26 unconfirmed, 73.7 percent of the confirmed, 27 cancelled missions counted beside; with the Personnel adapter down or in release 1.0 all 273 counted missions are unconfirmed and the percentage is not a number. Of the 626 crew references of the missions, 617 resolve and 9 have no entry (UNMAPPED), and a crew reference can reach a migrated civilian, who has no rank. The whole-stack compose now serves Missions release 1.1 and the snapshot `personnel-v2-large-004` by default, and the compose file that opted in to 1.1 was deleted. The commit is on the owned branch `tx/scale-up-rederive`, parent lab commit `81b759eecc0726994958788a7dc1b49e2c5f948e`, tree `959d03d`, 24 paths, +13266/-660. ## Choices recorded

- **The suite pages.** Every whole-list check asks offset 0, 100 and 200 with the graph's largest limit; no limit was raised. A page of 100 is two calls of the Missions adapter. `test_02` also checks windows across the Missions service's page boundary (50), the graph's (100) and the end, and that past the end is an empty list.
- **The warm-up, as the lead developer chose (A).** Before the first assertion the suite asks the three heaviest pages once and keeps the cold figures as facts. After that a normal page must answer in less than the least time a dead adapter takes (4.5 s) and carry no errors entry; the new `test_16` times the three full pages (1,258, 750 and 965 references). The 5 s timeout is unchanged.
- **A router can declare a second code for a dead adapter in a list.** Asked page by page, the Apollo router answered some later pages with `SUBREQUEST_HTTP_ERROR` (a connection refused at once) instead of waiting for `GATEWAY_TIMEOUT`, and both routers answered a page in 3.0 s. The setting `adapter_down_other_codes` lets a router declare such codes for lists; a single answer stays strict, and a list must still have one page that waited for the timeout. Apollo declares `SUBREQUEST_HTTP_ERROR`; Cosmo's entries have no code.
- **The small-data expectations are retired.** No test still runs on the small data, so `expected-outcomes.json` holds the large data only; the earlier file stays in Git history. The Missions adapter moved to release 1.1 and does not support both (the worker's choice, recorded here). The Missions adapter `service` stage (real Oracle) still pins release 1.0 and was not run.
- **Mapping release 1.2 is asked everywhere**, for the assets and the crew; releases 1.0 and the crew-in-1.0 cases are still asked on purpose (`NO_ENTRY`, UNMAPPED).
- **The Personnel container SOAP gate covers the large snapshot.** It now checks all four snapshots; for the paged package it compares the first page, every person by id, the traversal at four page sizes, every filter and the beyond-the-end pages with the authoritative pages (2,864 exchanges).
- **Texts.** The READMEs and the design document that named the small data as the stack's default were corrected, and the two router READMEs gained a section with the figures; the tables of the earlier runs stay as written.
