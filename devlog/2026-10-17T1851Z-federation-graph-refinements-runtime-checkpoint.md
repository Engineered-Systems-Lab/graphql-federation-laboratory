## Choices recorded

- **The mapping outcome is a field.** The mapping subgraph states `mappingOutcome: MappingOutcome!` on `AssetReference` and `PersonnelReference`, one enum for both kinds (`MAPPED`, `NO_ENTRY`, `RELEASE_REFUSED`). A refused release returns the entity with `RELEASE_REFUSED`, and the `MAPPING_RELEASE_REQUIRED` and `MAPPING_RELEASE_NOT_FOUND` errors entries stay beside it. The Assets and Personnel adapters read the id and the outcome through `@requires(fields: "assetId mappingOutcome")` (and the personnel equivalent), the `Resolution` enum has a fifth value `RELEASE_REFUSED`, and `MAPPED` without an id is a contradiction handled as UNAVAILABLE with `UPSTREAM_BAD_RESPONSE`. The lead developer chose this shape on 2026-10-17 (option B), for a clean design and implementation with fewer guesses.
- **The names.** The mapping's external asset id is `assetId` (the lead developer judged `astId` a poor choice and chose `assetId`); the crew one stays `personnelId`. The redundant `id` field is gone from both reference types: the mapped id is `assetId` or `personnelId`, the confirmed one is `asset.assetId` or `personnel.personnelId`. The experiment text of the integration notes that says `astId` is kept as written, with a later-context note, instead of being rewritten.
- **Asset.parent.** Resolved by the Assets adapter from its own service, one call per level and only when selected, with no federation feature beyond `@key`, no caching and no batching (the lead developer chose option A, to get as much value out of the graphs as possible). A parent id that does not exist gives null with no errors entry (the worker's proposal, shown in the preview); a failed call gives null with one `SERVICE_UNAVAILABLE` entry. Question 4 is now one query for the chain AST-0004, AST-0023, AST-0029.
- **A dead adapter.** Measured on 2026-10-17 with the Apollo router v2.18.0: the default 30 s gives HTTP 504 with data null; with `traffic_shaping.all.timeout` of 3 s or 5 s the router answers HTTP 200 with one `GATEWAY_TIMEOUT` entry per failed fetch naming the subgraph, roots of other subgraphs still answer, but the object that needed the dead subgraph is null because `resolution` is non-null. Apollo has no setting for partial data of a dead subgraph, so by the lead developer's rule (B if Apollo supports it cleanly, otherwise A) the setting is the shorter timeout, 5 s (about four times the slowest normal answer, 1.3 s). The lead developer accepted the stored value and left an environment variable for it as a future improvement. Making `resolution` and `asset` nullable would keep the rest of the object; it was not decided.
- **Queries that omit `resolution` and `asset`.** A selection of `localRef release assetId mappingOutcome` was answered with the Assets adapter stopped: the owning adapter is not called. A selection of `resolution` alone still makes the router ask the mapping subgraph first, for the `@requires` input.
- **Crew in release 1.1.** The whole-stack default of the Personnel service is `personnel-v2-small-003`, and the router acceptance asks the 56 crew references of the Missions dataset in release 1.1 (all MAPPED and RESOLVED, with the name, rank, department and clearance of the snapshot) and in release 1.0 (NO_ENTRY, UNMAPPED). The expectations are derived from the released files before any code.
- **Found, not decided:** a `@requires` of two fields, one an enum owned by another subgraph, composed with Rover 1.0.0 (supergraph 2.9.3) without a warning and worked under the router with no change of shape. `MappingReleasesTest.aSectionFileWithAnInvalidNameStopsTheLoad` fails with a local Maven on the Windows file system (a case-only rename) and passes in the Linux Docker build that the gates run.
