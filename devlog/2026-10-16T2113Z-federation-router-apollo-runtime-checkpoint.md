## Choices recorded

- **The supergraph is committed.** The lead developer's rule of the same day was to commit it if and only if a fixed build gives a byte-identical output and a small schema change gives a diff with no randomness. Both held: the SDL of each adapter was byte-identical on two fetches and after a restart; composing twice, from restarted adapters and through the start script gave the same SHA-256 (`115653f65211e9f09d154b9e6f2339538a6ce23cd82a931f603eeae260cfb68f`, 13,452 bytes); the reverse order of the subgraphs gave the same file too, because Rover prints types and fields alphabetically; adding one field to the Missions SDL changed exactly one line. A stack test composes again and fails when the committed file differs, so it cannot go stale unnoticed. There is no hash pin. The routing URLs are the service names of the stack, the same in every mode. The optional generated ownership table was not built.
- **The license acceptance stays with the person.** Rover's plugin is under the Elastic License 2.0. The Dockerfile, the composition script, the start script and the stack gate refuse unless `APOLLO_ELV2_LICENSE=accept` is set on purpose; the lead developer accepted it for this Job in their session. The plugin is stored in the image, so composing needs no network.
- **Two additive adapter changes, forced by composition and reachability.** Rover fails with `EXTERNAL_MISSING_ON_BASE` for `PersonnelReference.personnelId` unless some subgraph owns it, so the mapping adapter gained `PersonnelReference` with a `personnelId` that is null in every release; nothing returned a `PersonnelReference`, so the Missions adapter gained `Mission.crew(release)`. Every crew reference is UNMAPPED through the router with a null `personnel` and no errors entry (56 checked).
- **The acceptance tests follow the released files.** The Job text said EQ-97 and EQ-108 dangle as UNRESOLVED; the mapping release 1.0 and the Assets provenance say EQ-97 is UNRESOLVED and EQ-108 UNMAPPED, and the tests follow the files. The example "EQ-64 aboard SH-17" does not exist in the data; the chain checked is AST-0004, AST-0023, AST-0029.
- **Found, not decided:** a refused release (blank or unknown) shows each reference as UNMAPPED in the data, beside one error entry per reference, because the mapping answers a null entity and the Assets adapter derives UNMAPPED from the null id; question 4 cannot be one query because `Asset` has `parentAssetId` and no `parent` object; an adapter that is down gives HTTP 504 `GATEWAY_TIMEOUT` after the router's default 30 s with no data; with the Assets service down a mission answers with HTTP 200 and one `SERVICE_UNAVAILABLE` entry per failed call (65 entries for 65 mapped references of the whole list, since the router does not merge identical calls).
- **Checks:** the profile `federation-adapter-runtime` gained `federation-router-apollo-offline` and `federation-router-apollo-stack`, so every federation path now runs both. The stack gate needs the license acceptance in the environment.
