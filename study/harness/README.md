# Study harness

The agent loop for the two vendors, the scoring and the run manifests of the [Abstraction ladder study](../README.md). Raw transcripts go to the machine-local `LAB_RESULTS_DIR`, never into this folder. The method is in the [agent scenario design](../../docs/PLAN.md#agent-scenario-design).

The tests use fake vendor clients and fake stacks. The first real calls were the smoke and pilot runs of 2026-10-20 (see [the pilot](#pilot-2026-10-20)), on the lead developer's keys, started by the lead developer from their own terminal: the first paid request is the live check of the vendor request shapes, and `--dry-run` exercises everything else first.

## Models and settings

Two models, each through its own vendor API with the model id pinned. Each has one fixed request setting, recorded in every manifest and never tuned per scenario or task (`models.json`):

- `claude-sonnet-5-5`: adaptive thinking and effort `medium`, the starting point Anthropic's prompting guide gives for agentic tool use.
- `gpt-6.1-sol`: reasoning effort `medium` (its default). Tool calling works through the Responses API only, which is the one the client uses.

The SDK pins are in `requirements.txt` (`anthropic` 1.16.0, `openai` 3.35.1, `mcp` 2.3.0). SDK retries are switched off, so every retry is the harness's own, recorded and costed. Prompt caching differs by vendor and is not a setting: the OpenAI API caches repeated prefixes by itself, while the Anthropic client marks the end of the last message of every request with a cache breakpoint, so each turn of a run reads the earlier turns from the cache. Both are costed from the cached-read column of `prices.json`.

## The loop and the scoring

One shared system prompt for every scenario and model (answer with the tools you have, then call `submit_answer`; say so if something cannot be determined). Beta adds the guide document to that prompt. The tools are the scenario's MCP tools plus `submit_answer` with the task's fixed schema, and, when the config names them, the [harness tools](#the-harness-tools). The answer is scored by the corpus scorer (`study/corpus/scoring.py`, loaded from the corpus folder; no judge) through the [scoring contract](#the-scoring-contract). A format error is tagged apart from a wrong answer. The task text is read from the corpus at run time and is copied nowhere.

Limits, the same for every scenario and model and configurable: tool calls, wall-clock seconds and tokens per task. Hitting one is scored `did_not_finish` with its reason, and everything spent is counted. A text-only reply is nudged to submit up to `max_nudges` times, then `did_not_finish` (`no_submission`). The numbers are set from the pilot, at about twice Alpha's worst pilot run.

## Token budget

The budget is in tokens per vendor, with input, cached read, cache write and output counted apart and never twice. The dollar estimate beside it comes from `prices.json`, which is dated; dollars are derived and never stored as raw data. Rules, from the lead developer and the Coordinator:

- Before each request the harness reserves its possible cost (the estimated current input plus the maximum output). A request that does not fit is a clean **budget stop**.
- Every reservation, settlement and retry is appended to the ledger (`budget-<vendor>.jsonl`) at once, and every vendor request is timed on its own (`requestStart`, `requestEnd` and `requestSeconds`, with no tool, ledger or scoring time in it) on the assistant turn of the transcript, on each retry event and on its settlement entry. A reservation that was never settled (the process died during a request) is charged in full on resume.
- A completed run is saved the moment it finishes. A budget stop ends the study cleanly with everything kept and the incomplete run archived under `attempts/`, never overwritten.
- `--resume` runs only the missing or incomplete runs and refuses a study whose plan, models, limits, prompt, guides, corpus or prices differ from the stored manifest, and one whose [provenance](#run-provenance) differs from what was declared or observed before. Since 2026-11-05 (the Job `study2_prerun_fixes`) it also refuses when any Python file the run executes differs from the stored manifest's `codeFiles` (added, removed or changed, each named), so one manifest never covers runs of two versions of that code. `codeFiles` holds the SHA-256 of, by path from the repository root: every non-test `*.py` of `study/harness`; the MCP servers `study/mcp/mcp_core.py`, `raw_server.py`, `adapters_server.py` and `graph_server.py`; `study/launch/launch.py` (the stack, health, ready and fingerprint commands); `study/preflight/preflight.py` (which the real-mode fingerprint imports); and the scorer `scoring.py` of the corpus the run uses. The corpus manifest and the guides are in the plan identity already. The `commit` and `treeDirty` are recorded for provenance but not compared, so a records-only commit (a devlog entry, evidence) between a stop and its resume does not force a new study run. Before, two runs of different calculator code could share one plan hash (`study2-confirm-v5-dry1` and `-dry2`), and a resume would have mixed them.
- **What the plan identity binds of the corpus and the analysis** (Job `study2_freeze_code`, 2026-11-06). `corpusFreeze` is the SHA-256 of the corpus's `corpus-manifest.json`, and corpus 2's manifest lists the hashes of all seven files the scored run reads: `pool.json`, `ambiguity.json`, `dev.json`, `keys-a.json`, `tasks.json`, `schemas.json` and `expected.json` ([corpus 2](../corpus2/README.md#files)). A config with a `schedule` (study 2) must name its analysis plan (`analysis_plan`, a path; `study/launch/make_config.py` names `study/analysis2/PLAN.md` for every study-2 config), and one that names none, or a file that does not exist, is refused at the start. The plan identity then holds the plan file's SHA-256 (raw bytes) as `analysisPlan` (decision C3), so every manifest records it, a resume refuses a changed plan and the analysis refuses a bundle whose `analysisPlan` is not the hash of the plan it runs under. A config without a schedule, as study 1's, names none and gives an unchanged plan hash. `hash_files` (`datasetHashes`) stays recorded but not compared.
- **How a refusal of a resume exits** (decision C4). Every refusal of `Study.run` that the stored manifest decides (a run that exists without `--resume`, a changed plan identity, changed code, a stored manifest without provenance, changed provenance, and a changed dollar ceiling with the same `ceiling_basis`) raises `ResumeRefused`: nothing is written, and the runner prints `STOP: ` with the message, then `Study run <id>: resume_refused`, and exits 3, like `budget_carry_refused`, `provenance_refused`, `fingerprint_refused` and `scoring_error`. The messages are unchanged. Before, these refusals exited 1 with a traceback.
- The pilot budget was 20 dollars per vendor. Study 2's ceiling (decision D of the [design](../../docs/STUDY-2-DESIGN.md#cost)) is 125 dollars for all of study 2, development included, split as 85 dollars for Anthropic and 40 for OpenAI; the example config sets `dollar_ceiling` to these. Put the matching token figure in the config (`budgets.<vendor>.tokens`, no default). Verify that each vendor console enforces its own cap; the harness enforces its own stop regardless.
- **The ceiling across study runs** (with a `schedule`; decision F1 of the Job `study2_build_followups`, 2026-10-29). The ceiling covers all of study 2, so a later run counts the earlier runs' spend:
  - Every vendor budget carries `dollar_ceiling` and `ceiling_basis`, the text the ceiling rests on: decision D, or the lead developer's dated raise. Both are required.
  - `earlier_study_runs` lists the ids of the earlier study-2 runs in the same `LAB_RESULTS_DIR` (development and preflight runs included). At the start the harness reads their `budget-<vendor>.jsonl` ledgers without writing to them, prices them with each run's own manifest (a reservation never settled at the output price) and counts the total against the ceiling from the first request. The manifest records it as `budgetCarry`: the run ids, each ledger's SHA-256, dollars and tokens, and the totals per vendor. The list is in the plan identity.
  - A listed run without a manifest, or with a ledger of a vendor its manifest does not price, refuses the start (`budget_carry_refused`, exit 3), before anything is written. A resume whose earlier ledgers no longer hash as recorded is refused the same way.
  - A resume with another `dollar_ceiling` or `ceiling_basis` records the old and new values in `resumes.jsonl` (`ceilingChanges`, and the `ceilings` then in force). A changed ceiling with an unchanged basis refuses the resume: a raise needs its basis.
  - The carry is in dollars against `dollar_ceiling`; the token figure stays per run. The budget snapshots add `carriedDollars` and `dollarCeiling`.
- The harness prints its budget once, at the end of a run. To follow the spend, the room under each ceiling and an estimate of the rest after every block, without seeing any outcome, run the launch kit's read-only [watcher](../launch/README.md#watching-a-run) beside it.

## The run protocol

One stack run per scenario (the whole plot), with the models nested inside it (the sub-plot), sequentially. Per scenario: start the stack through the config's commands, wait until the MCP server answers, record the cold start and the cold first request, run the declared warm-up (`warmup_passes` passes over `warmup_calls`), then run every task and trial of the set with every model, and tear down. The order of the tasks and trials is shuffled from the recorded seed. The model order is interleaved per task and counterbalanced by cycling the model permutations from a seeded start. A category D task stops its service before its runs and restores it after. Every sample carries its phase (`cold`, `warm-up`, `measurement`) in `samples.jsonl`. A budget stop ends the whole study, so the order stays balanced for the resume. Subprocesses of the stack get an environment without the API keys.

Records, in `LAB_RESULTS_DIR/<study run id>/`: `manifest.json` (the commit, SDK versions, harness file hashes, models with their settings and price entries, prices date, limits, budgets, telemetry and router settings, dataset hashes, machine facts, stack facts, the declared provenance, the scoring contract, the plan and its hash, and with the schedule or the harness tools the fields listed below), `samples.jsonl`, `budget-<vendor>.jsonl`, `runs/<key>/transcript.jsonl` and `result.json` (with the harness tools also `results.jsonl`), `provenance/<scenario>.json` and `provenance/checks.jsonl` (with the schedule also `provenance/<block>.json` and `blocks.jsonl`), `scores.jsonl`, `scores.csv` and `bundle.json` with the checksum. Nothing written holds an absolute path or a key; the exact key values are also redacted from everything the harness writes. The MCP servers' call logs are matched to a run by the `X-Study-Run-Id` header, which carries the run key.

## The block schedule (study 2)

With a `schedule` block in the config the harness runs [study 2's design](../../docs/STUDY-2-DESIGN.md#the-schedule-a-williams-square-in-four-rounds) instead of one stack run per scenario. A config without it runs exactly as before, with the same plan, plan hash, outcomes and score columns.

| Config key | Holds |
| --- | --- |
| `schedule` | `{"design": "williams-4-half", "arms": [four scenarios], "reference": <scenario>}`: the four full arms of the square and the Direct Access reference block. `scenario_order` and `trials` are then not used. |
| `seed` | The one seed; the schedule's draws use sub-seeds of it by label (letters, rounds, halves, models per half, the order of each block). |
| `dataset_fingerprint` | A command, run at every block start, that prints one JSON object with two texts: `fingerprint` (the dataset) and `session` (one continuous run of the database, for example its instance start time). Required with `schedule`. |
| `scenarios.<arm>.health` | A read-only command that probes every backend of the arm and prints one JSON object `{"backends": {"<backend>": {"up": true or false, "detail": "..."}}}`, one entry per backend the arm's provenance declares. Required for every scenario of the schedule. See [the void-block rule](#the-void-block-rule). |
| `scenarios.<arm>.ready` | `{"<service>": command}`: a read-only command per outage service that asks the service once through the arm's entry point and prints `{"ready": true or false, "detail": "..."}`. Required under a schedule for every service a task of the set stops; the commands are in the plan identity. See [the void-block rule](#the-void-block-rule). |
| `health_every_runs` | Optional, default 10: the health check runs again after every so many runs of a block. Fixed for the study run (it is in the plan identity). |
| `budgets.<vendor>.ceiling_basis`, `earlier_study_runs` | The ceiling across study runs, see [the token budget](#token-budget). |
| `harness_tools` | Optional: `["calculate", "ask_requester"]`, see [the harness tools](#the-harness-tools). It also works without a schedule. |
| `corpus_dir` | Optional: the corpus folder the harness reads, which the [launch kit](../launch/README.md#the-study-config) writes (`study/corpus2` for a schedule). The runner's `--corpus-dir` may name the same folder, and another folder is refused; with neither, study 1's `study/corpus` is read. |

A corpus task may carry `set` (`core` or `ambiguity`), `size` and `systems`; `load_tasks` passes them on and the halves are stratified on them with the category.

**A task subset.** `task_set` is `dev`, `scored` or a subset of one of them, `{"set": "dev", "tasks": ["V05", "V06"]}`, which runs only the named tasks, in the set's own order, with or without a schedule. Every id must be in the set and named once, and no other key is accepted. `task_set` is in the plan identity, so the manifest records the subset and a resume refuses a changed one.

**The schedule,** computed from the config and the seed in `schedule.py`, so the same seed always gives the same schedule:

- The square is the design page's: rows `a b d c`, `b c a d`, `c d b a`, `d a c b`. Every arm stands once in every position and directly follows every other arm once.
- A seeded draw assigns the four arms to the letters, and a seeded draw orders the four rows in time. Rows 1 and 3 run half H1 and rows 2 and 4 run half H2, whatever order the rows run in.
- The halves: the tasks are grouped by stratum (set, category, size, systems), shuffled within each group and dealt alternately, so every stratum splits evenly within one task.
- The model split: within each half, dealt the same way by category, each task runs with one model in one of its two rows and with the other model in the other row, the same model for all four arms of a row. Every arm thus runs every task once per model.
- Inside a block the tasks are shuffled from the block's own seed, which also places the outage tasks, and the models alternate. The reference block comes last: every task with both models, the models interleaved per task.
- Run keys are `<arm>__<task>__<model>__r<row>`, and `__ref` in the reference block.

**A block** is one start of its arm's stack. The harness starts the stack, waits until it is ready, then, before the warm-up and before any paid request:

1. observes the provenance again, compares it with the declaration and with the arm's first stored observation, and keeps it as `provenance/<block>.json` with a line in `provenance/checks.jsonl`. A mismatch or drift refuses the block. A declared backend found down, and nothing else wrong, is a void trigger instead (the check's line says `down`).
2. runs the fingerprint command. The block is refused unless the fingerprint equals the study's first fingerprint and its session's first one. The session is recorded on the block's line in `blocks.jsonl` and on every run of the block.
3. records the start of the block's current attempt and runs the arm's health check.

A refusal tears the stack down, writes the bundle with status `provenance_refused` or `fingerprint_refused` and exits with 3. Then the block runs its runs in order, stopping the outage service around each of its runs. A run that ended on a vendor error is queued again once, at the end of its block, and a second vendor error is recorded as the outcome `vendor_error`, which is missing from the main analysis (its score is empty). The count of vendor errors comes from the run's result and its archived attempts, so the requeue survives a stop. `blocks.jsonl` has a line for every block start (with the attempt, the session, the fingerprint, the provenance fingerprint and the start number), refusal, budget stop, void and end (with the outcomes), each with the block's `attempt`.

**Resume.** `--resume` goes through the blocks in order, skips every block whose runs are all finished and whose current attempt ended, without starting its stack, starts a partly finished block again and runs only its missing runs, the requeued ones last. A block whose runs are all finished but whose attempt has no `end` (the process stopped before the end check) is started again, runs nothing and ends. After a void the resume repeats the block whole as the next attempt. The refusals on a changed plan (the schedule included) or a changed provenance are unchanged.

**The manifest** adds `schedule` (design, seed, square, letters, round order, the half of each row, the halves, the model of each task per row, and every block with its sequence, row, position, letter, arm, half and runs in order), `stackRunsPerBlock`, `vendorErrorRequeues`, `datasetFingerprint` (the command, redacted, and the rule), `voidRule` (the health interval, every arm's health command redacted, the check points, the declared triggers, the excluded window and where void runs go) and `budgetCarry`. The schedule, the redacted fingerprint command, the health interval and commands and the earlier study runs are in the plan identity. Each run's record adds `block`, `blockSequence`, `row`, `roundSequence`, `position`, `half`, `orderInBlock`, `session`, `requeued`, `vendorErrors` and `blockAttempt` (the block's attempt; `attempt` stays the run's own attempt, counted again within each block attempt), and the scores files carry them as columns.

### The void-block rule

The design (["Exclusions"](../../docs/STUDY-2-DESIGN.md#the-scoring-contract)): "A block in which the provenance or health check finds a backend down outside a category D task is void and repeated whole. The trigger is declared, not judged." The lead developer decided how on 2026-10-29 (decisions F2 and F3 of the Job `study2_build_followups`):

- **Attempts.** Every block event carries `attempt` (1, then one more after every void of the block); a resume continues the current attempt.
- **The health check** is the arm's `health` command, run at the block start, after every restore of an outage task's service, after every `health_every_runs`-th run of the block (counted within one start of the block; after an outage run the restore check stands for it) and at the block end. Every check is a line of `health.jsonl` (block, attempt, point, result `up`, `down` or `unreadable`, the backends and the problems). It is not run while an outage task's own service is stopped, which is the excluded window. Known limit: a backend that drops and recovers between two checks is not seen.
- **Readiness after an outage.** After an outage task the service is started again, then the harness waits, within the scenario's `ready_timeout_seconds`, until the MCP server lists its tools, the health check passes for every backend and, since 2026-11-05 (the Job `study2_prerun_fixes`), the arm's `ready` command for that service finds it answering through the arm's own entry point: the router for Apollo and Cosmo, the adapter for GraphQL Adapters, the service's published port for the direct arms (`launch.py ready`). The MCP wait and every probe get only what is left of that deadline, and an answer that comes after it does not count. The passing check, or the last failing one, is recorded with its number of polls, and the entry point's last answer with its own polls as `entryPoint` on the same line of `health.jsonl`. The reason: on delta on 2026-11-05 the health check passed the moment Assets was back while the router still answered `SERVICE_UNAVAILABLE` for Assets for about 6 seconds, in two of four restores, so the next task, which is not an outage task, could have met an outage that voids nothing.
- **The triggers,** declared in the manifest: the provenance observation at the block start finds a backend down (no container, or not running, together with the routing lines of its own declared endpoints and variables that this causes; any other routing fault still refuses the block); a health check finds a backend down or cannot be read; a restore that does not come back in time (the service, the MCP server, every backend or the arm's entry point for the service).
- **On a void** the harness appends a `void` event (the block, the attempt, the trigger, the point, the problems, the session, the run keys and their spend per vendor), moves the attempt's run folders (those whose result names that attempt, and an unfinished one only before a later attempt has started) to `runs-void/<block>/<attempt>/`, so no void result stays a run's current result or a row of the scores, tears the stack down and stops with the status `block_void` (exit 3) and the bundle written. The operator checks the backend and resumes; the resume repeats the block whole, from no finished run, as the next attempt. A move cut short is finished by the next resume.
- **Spend.** The void attempt stays in the vendor ledgers, because it was billed, and counts against the budget. `bundle.json` reports it apart as `voidAttempts` (the attempts and the spend per vendor).
- A stack that does not become ready at the block start still stops the study as before, with nothing recorded for the block.

## The harness tools

`harness_tools` in the config offers two tools beside every scenario's MCP tools ([the design's tools](../../docs/STUDY-2-DESIGN.md#the-tools)), the same name, description, schema and limits in every arm and run. A scenario whose MCP server already has a tool of either name is refused before any paid request.

The tools are version 5 (the Job `study2_calculate_v5`, decisions W1 to W5 of 2026-11-05), one strictness pass from an independent audit of every `calculate` call of the four paid runs ([the audit](../evidence/study-2-trap-audit/REPORT.md)), after version 4 (decision V1 of the Job `study2_calculate_v4`, 2026-11-04) failed the declared tool check on one new kind of failure, seven intersections with a record field over a source of plain ids that returned 0 without a word; version 3 (decision Q1 of the Job `study2_calculate_v3`, 2026-11-04) had failed it on a filter on fixed list positions, because a condition could not test every element of a list; version 2 (decision R1 of the Job `study2_calculate_redesign`, 2026-11-03) had failed it on its token-volume clause and with a new kind of failure, and version 1 on its token-volume clause.

- **Result ids.** With `calculate` offered, every result of a scenario tool and every successful `calculate` result gets an id `<tag>-<n>`, where the tag is four hex digits of the run key and attempt and `n` counts from 1. The id is shown to the agent as the result's first line, `result_id: <id>`, and the result is stored unchanged in the run's `results.jsonl`, which the bundle checksum covers.
- **Stored results.** With `calculate` offered, a scenario result longer than 5,000 characters (`storeAboveChars`) is stored in full and not shown. The agent reads its id line, then `stored, not shown: <n> characters.`, its shape and one line on `view`. The shape is the result as `calculate` reads it (JSON in a text decoded, XML read generically), with every list cut to its first element and `... <n> elements in all`, every object to its first 20 keys and `<n> keys in all`, every text to its first 120 characters and its length, and the whole within 1,500 characters, cutting depth first. Version 3 stores a `calculate` output longer than 5,000 characters the same way, below its read line (see below); a shorter result is shown in full. The rule knows only sizes and shapes, so it is the same in every arm. `results.jsonl` marks each result `shownInFull` true or false, and the transcript event of a stored result, a `calculate` output included, carries `stored`, `storedChars` and `shownChars` in `harness`.
- **`calculate`** names one or more results by id, each with an optional path, and one generic operation: `view` (the part at the path of one source; `offset` and `limit` page through a list, the keys of an object or the characters of a text, and `fields` shortens the records of a list; a page holds at most 5,000 characters (`viewPageChars`), ends earlier when the window asked for is longer, and carries `nextOffset` while the part goes on, so a page is always shown in full and never stored; every key the page carries, `missing` and `nextOffset` included, counts toward its size; a single record or key longer than a page is shown as its shape and named in `shapeOnly`, a key longer than 120 characters as its start and its length, and a deeper path reads it), `count`, `distinct`, `group_by` (count or sum; since version 5 an empty `group_by` list gives one group over all records, also when there are none), `sort`, `filter` (literal `eq`, `ne`, `lt`, `le`, `gt`, `ge`, every condition must hold; since version 4 a condition with `elements` `any` holds when at least one value at its field satisfies the comparison, and with `elements` `none` when no value does: the values are found as a source's path finds its records, `*` taking every element of a list, a list at the end giving its elements and an element that lacks the rest of the field left out, so an empty list or a missing field has no values; a condition whose field has a path segment that is exactly `*` and no `elements` is refused with `Wildcard fields require elements: "any" or "none".`, where version 3 treated such a field as missing, which could silently include or exclude records depending on the comparison; that refusal is the one deliberate exception, asked for by the lead developer, to keeping every existing condition unchanged, and an asterisk inside a key name is not a segment; every other condition without `elements` is unchanged), `union`, `intersection`, `difference` and `arithmetic` (add, subtract, multiply, divide over numbers or results). `fields`, `limit` and `round` shorten the output. An output is kept whole up to 5,000,000 characters (`maxStoredOutputChars`, the most a source may hold, so a stored output stays readable as a source); past that version 5 refuses the call, where version 4 cut the output and marked it `truncated`. Version 2 cut every output at 50,000 characters, so a calculation over a cut output read only part of it. A path is dot-separated keys or positions, with `*` for every element of a list; since version 5 a step in brackets is one key taken literally, dots included (`[a.b]`), and an output names a field as it was written. A text on the way is read as JSON, or as XML when it starts with `<`: XML is read generically, with local tag names, attributes as `@name` and a repeated element as a list, so the SOAP arms can use the tool like the others. It has no network, file, database, backend or answer-key access and sees only the run's own results. An id of another run, an unknown id, an operation or comparison not on the list, an `elements` other than `any` or `none`, a `*` field without `elements`, a text on a condition's field that cannot be read and a bad path are refused as tool errors, and version 5 adds the refusals below.
- **The read line.** Every successful `calculate` output starts, after its id line, with one line `read: ` naming per source, in the order given, the result id, the path (`at "<path>"`, or `at the whole result`) and what it contributed: `<n> records`, or for `view` `an object of <n> keys`, `a text of <n> characters` or `one value`, and for an `arithmetic` operand `one number` (`read: no result (numbers only)` when every operand is a number). It adds `(the path matched nothing)` when the path found nothing at all (an empty list that is found gives `0 records` without it) and, when elements after a `*` lacked a step, since version 5 the step they lacked: `(<k> elements lacked "<step>" and were left out)`, or `(<k> elements were left out: <n> lacked "<step>", ...)` for several steps. It never adds the sources up, because sources can overlap. A refusal has no read line. `results.jsonl` keeps the line as `readLine` beside the output, and the transcript event as `read` in `harness`.
- **Version 5: what is refused.** The output of a call that both versions accept is the output version 4 gave, with one exception that is new syntax: a step in brackets, which version 4 read as a key with the brackets in its name, names the key inside them where no object of the call has version 4's key, so such a call gives a value where version 4 gave null; what else changes is which calls are accepted and the lines around the output. A refusal names every problem of the call at once (`<n> problems: (1) ...; (2) ...`) and, where a problem is one of shape, ends with `Shapes:` and the shape of each source (its records and their keys, or that it holds plain values) or of the result a bad path was read from; it is at most 1,500 characters (`refusalChars`). Refused are: an argument of the wrong form, named with the form it takes (`limit is a whole number of 1 or more (got "two")`) in place of version 4's `the calculation failed (TypeError)`; a key that a source, a condition or an operand does not take; an argument that does not apply to the operation, where null, false, an empty text or list and offset 0 count as not given; a field on a source of plain values, with the path to use instead; a field that no record of any source has, with the instruction to choose one of the keys named under `Shapes` or to correct the path, in `view` with `fields` as in every other operation, except in a condition that compares the field with null, which is the test that a field is there and is answered, with the records that lack it named in the coverage line; a `*` in a field outside a filter condition with `elements`; a `*` at an object, where an object read from an XML element still counts as a list of one, because XML has no lists; a list or an object compared with one value that is not null, without `elements`; two conditions that contradict each other (the same test with `elements` `any` and `none`, or a comparison and its opposite on one field and value); a key with a dot in its name spelled as nested steps, with the bracket form to write; and a step in brackets that the objects of one call answer by more than one key. Version 4 had no brackets and read `[x]` as the key `[x]`: where the records of a call have that key, that reading stands for every one of them, so a call version 4 answered keeps its answer. A step in brackets is read one way in a whole call, by every record for a field and by every source and operand for a path: a call in which some records have the key `[x]` and others the key `x` is refused, because reading `x` there would change the answer version 4 gave for the records beside them.
- **Version 5: the coverage line.** After the read line, and only when there is something to say, one line `coverage: ` of at most 600 characters (`coverageLineChars`): per field that some records lack or hold null, how many records have it, with the sources that differ; a condition that holds for records without its field; what each condition did alone when a filter kept nothing; the records a sum added; a null among distinct or set values; the size of each set, in the order of the read line's sources; groups over several fields that are not unique values of one field; and, when a list the sources read states `totalCount`, `total` or `hasMore`, or a source reads a calculate output that a limit or a view page shortened, that the sources hold fewer records than the total states, or more. That last fact stays with every output built from the source, an arithmetic result included. It never says that a list is complete, and it says that records are missing only when that is certain. Nothing a result holds can show that two lists of one name are not pages of one list: one result can hold several pages of one list under different keys, as a graph query with aliases gives them; a page need not state the total, or anything at all; and two requests can ask for other fields of the same records, or for another order. So every list a source reads is taken, and the lists of one name count together, with the records that a source reads as elements of other lists of that name (through deeper lists, or through a `*` before any list). A list is short only when all of these records are fewer than the total it states; where the lists state several totals the line says `at least <n> not among the sources`, because the records of one may be the records another lacks. A list is known by the keys that lead to it, so a list under a key with a dot in its name and a list under nested keys are two lists, and a `*` at an XML element that occurs once is walked through to the list inside it. Records are counted as the pages hold them. They are told apart by the plain values that every record of every page has, so the same records asked for with other fields are seen as the same; where there is no such value, or a page holds two records alike in them, every record counts. With one total and as many records as it states or more, the line says three things as they are and concludes nothing: more distinct records than the total; fewer distinct records, with the condition that makes them a shortfall (`if pages overlap`); and as many records from several pages when two of the pages state the same place (the same `offset` or `page`, or each the last) and share no record, when every page says `hasMore`, or when no page states its place. Otherwise it says nothing. Pages of two lists of one name and total that state different places cannot be told apart. A field that every record has is not named either, so that the line stays short.
- **Version 5: warning lines.** At most two lines `warning: ` of at most 300 characters each (`maxWarnings`, `warningChars`), never a refusal, for what only the agent can judge: a calculation that repeats one already held, with the earlier result id; a scenario result that is the same as a held one, or whose list of ten or more records is held already with all its keys and values (`repeatMinRecords`); held pages of a list the sources leave short that are not among the sources (the same tool, list name and record keys, stating the same total or none), named by the result that holds them and counted, because that result can itself be among the sources for another of its pages, or a held list that holds the records the sources read and more; and conditions on fixed positions of a list that has more elements, with the `elements` condition that tests them all. The lines of a calculate output count toward the 5,000 characters at which it is stored; a view page keeps the size version 4 gave it and carries its lines above it. `results.jsonl` keeps them as `coverageLine` and `warnings`, and the transcript event as `coverage` and `warnings` in `harness`.
- **`ask_requester`** takes a question, logs it with the run key and always returns "No requester response is available during this evaluation."
- **Logging and counting.** Both tools count in the tool-call limit like any other tool. Each call's transcript event carries `harness`: for `calculate` the result ids used, the operation, the new result id or the failure, the seconds of the calculation, the bytes read and returned and an estimate of the tokens it added; for `ask_requester` the question and the run key. The run's record adds `harnessToolCalls` (`calculate`, `calculateErrors`, `askRequester`) and `askRequester` (the questions), and the scores files the columns `calculateCalls`, `calculateErrors` and `askRequesterCalls`.

The manifest and the plan identity record the tools as `harnessTools` (the version, names, descriptions and schemas, the fixed text, the id format, the operations, the limits, the stored-result rule, the read-line rule, the element rule `conditionElements` and version 5's rules `refusals`, `coverageLine` and `warningLines`), so runs of different versions never share a plan hash.

## The scoring contract

`scoring_contract.py` declares how the harness calls the corpus's `scoring.py` and what it accepts back.

| Version | Declared by | Called as | Outcomes the scorer may return |
| --- | --- | --- | --- |
| 1 | nothing (study 1's corpus, unchanged) | `score(submission, schema, expected)` | `correct`, `wrong_answer`, `format_error`, `silent_guess`, `definition_not_accepted` |
| 2 | `SCORING_CONTRACT = 2` in the module (corpus 2) | `score(submission, schema, expected, context)` | `correct`, `wrong_answer`, `format_error`, `definition_not_accepted`, `abstained` |

- `context` holds `taskId`, `set`, `category` and `askRequester`, the run's log of `ask_requester` questions, which is the only source of a clarification. A version-2 scorer may also return the booleans `clarified` and `interpretationAccepted` for the ambiguity set; the scores files carry them as columns.
- Every result must carry an outcome of its version and a `score` that is 1 exactly when the outcome is `correct`. A result that breaks the contract stops the study (bundle status `scoring_error`, exit 3); it is never recorded as a score.
- The harness decides two outcomes itself: `did_not_finish` (no submission, or a limit) and `vendor_error`. `budget_stop` is not a score.
- `abstained` is incorrect for primary accuracy and reported as its own outcome beside wrong answers. Which submissions count as abstention is decided by corpus 2's scorer and frozen with it.

The manifest records the contract as `scoringContract` (version, outcomes, the correct outcome, the harness outcomes and the scorer's SHA-256). A version other than 1 is part of the plan identity.

## Run provenance

Study-1 ran against a Missions simulator instead of the Oracle-backed service, and nothing in its manifest said so. Every run now declares the backends it means to use, observes the ones it actually uses, and refuses to spend anything when the two differ.

**Declare.** Every scenario of the config has a `provenance` block, and a scenario without one is refused when the config loads. `study-config.example.json` shows the shape:

| Key | Holds |
| --- | --- |
| `compose_projects` | The compose projects the harness observes. |
| `backends.<logical service>` | `mode` (`real` or `simulated`); `service`, the compose service that serves it, as `name` or, when two projects have that name, `project/name`; `image_id` (`sha256:...` from `docker inspect`) and/or `image_ref` (the image name the container was started from); optionally `dataset`: `id`, `path` (a file or a folder the harness hashes), `sha256` (expected) and `mount` (the container path of a bind mount that must exist on that service and whose source the harness must be able to read and hash; leave `mount` out where it cannot, as with some Docker Desktop paths). |
| `service_images.<compose service>` | Optional: the pinned image of a compose service that is not a backend (the launch kit pins the four adapters and the Assets bootstrap here). `image_id` (`sha256:...`, required), optionally `image_ref`, and `one_shot: true` for a container that runs once: it passes when it is running or has exited with code 0, its normal completed state, and fails in any other state. Every other service must be running. Checked at every observation, so at every block of a schedule, like a backend's `image_id`. |
| `routing.endpoints` | Each upstream URL the MCP server calls, with the compose service that must publish its port on the host. The host must be `127.0.0.1`, `localhost` or `[::1]`, and the port must be published on an address that serves it. |
| `routing.env` | Per compose service, the backend URL variables and their expected values (for example `MISSIONS_SERVICE_URL`). |
| `launch_files` | Label and path of the launch scripts and config files to hash. Only the hash is stored, never the contents. |

**Observe.** After the stack is ready and before the warm-up, so before the first paid request (dry runs included), the harness runs two read-only commands and nothing else: `docker compose -p <project> ps --all --format json` and `docker inspect` of the containers it lists. Per service it records the state and the exit code (`State.ExitCode`), the image ref and id, the published ports, the routing environment (names that end in `_URL`, `_HOST` or `_PORT`, and every name in `routing.env`) and the bind mounts (the container path and the SHA-256 of the source when the harness can read it; the source path is never stored). It also hashes the datasets and the launch files and records the scenario's stack commands as the launch configuration.

**Compare.** Any difference refuses the scenario before any paid request, with one line per difference: a backend service that is missing or not running, another image, a pinned service image that differs (a line that starts `pinned image of`), a one-shot service that exited with another code than 0, a dataset hash, a missing mount, a mount that cannot be read or whose hash differs, a routing variable, an endpoint port that the named service does not publish, a launch file that cannot be read, or a stack that cannot be observed. `mode` is recorded as declared and checked through the service, image and routing it implies. The stack is torn down, the bundle is written with status `provenance_refused` and the command exits with 3.

**Keep.** The manifest holds `provenance.schema`, `provenance.intended` (each scenario's declaration, host paths reduced) and `provenance.observationCommands`. The first matching observation of a scenario is `provenance/<scenario>.json`, with a `fingerprint` of its stable part (images, routing environment, ports, mounts and hashes, datasets, launch files, launch configuration and the MCP URL; container ids and times are left out). Every later check, and every refusal, is a line of `provenance/checks.jsonl` (`match`, `mismatch`, `drift` or `unobserved`). The bundle checksum covers both.

**Resume.** A resume refuses when the declaration differs from `provenance.intended` and when a scenario's new observation differs from its stored one, naming each change. There is no override. A bundle written before provenance existed cannot be resumed.

**Redact.** Environment values whose names contain `PASSWORD`, `SECRET`, `TOKEN` or `KEY` (in any case, which covers both API key names) are stored as `[MASKED]` with the name kept, and so is the value of a command option with such a name (`--db-password x`). The `user:password@` part of a URL is masked, in the observation and in the declaration the manifest keeps. Host absolute paths are reduced to `<path>/<last component>`; container paths, such as mount destinations, stay. The exact values of the API keys are redacted from everything as before.

## Credentials

The two keys are generic credentials in Windows Credential Manager under names that do not depend on any repository:

| Vendor | Name | Variable the child receives |
| --- | --- | --- |
| Anthropic | `agent-study/anthropic-api-key` | `ANTHROPIC_API_KEY` |
| OpenAI | `agent-study/openai-api-key` | `OPENAI_API_KEY` |

Setup, once, by the lead developer in a PowerShell terminal (the keys are typed hidden, twice, and never appear in an argument, a file, a log or the shell history):

```powershell
py -3 study/harness/launcher.py --set-credentials
py -3 study/harness/launcher.py --check
```

`--check` prints present or missing for each credential and never a value. One command then runs a whole pilot or study run, the launcher starting the harness with the keys in the child process only:

```powershell
py -3 study/harness/launcher.py run -- --config <machine-local config> --run-id <new run id>
```

`--dry-run` after the `--` runs the whole protocol with a fake vendor client that spends nothing. If a key is missing the launcher looks first, then asks (hidden, twice, sanity check of the prefix and shape only, no API call) only in an interactive terminal; anywhere else it stops with a clear message, so a worker session never receives a key. `--set-credentials` replaces a key after a rotation. The launcher changes no global or user environment variable, no shell profile and no coding-assistant authentication. The harness itself reads the keys from the environment only, so explicit process-level injection works everywhere. Limitation: Credential Manager protects storage; it does not restrict retrieval to this application. Windows is implemented; the stores of other operating systems are deferred until they can be tested.

## Pilot (2026-10-20)

The pilot ran the development set (4 tasks) in Alpha and in Delta (Apollo) with both models, one trial: 16 runs in the run `pilot-1`, status complete, no retry, no budget stop, code at the commit that times every request. Bundle checksum (from `bundle.json`): `88629e9e8eb2560948d8ce84993fe170589a3ab018cafbbeb29cc80c3048c217`. The bundle stays machine-local in `LAB_RESULTS_DIR`. The scored corpus is frozen with the manifest checksum `e0e019c2987a9c3b81fa1602953df9cc6269f6af34dc1f3247136c886321651f` (see the [corpus freeze](../corpus/README.md#the-freeze)). Spend at the dated prices: about 0.83 dollars for Claude Sonnet 5.5 and 0.26 for GPT-6.1 Sol. Correct answers: 3 of 4 in Alpha and 4 of 4 in Delta, for each model. The two Alpha misses are one run that hit the tool call limit (Claude) and one name answered with a rank in front (GPT).

Settled for the study, by the lead developer:

- **Limits per task:** 80 tool calls, 1,000,000 tokens with cached reads counted (the cap is checked before each request) and 900 seconds of wall clock. The retries and nudges are unchanged.
- **Trials:** two, which is 320 runs (5 scenarios, 16 scored tasks, 2 models). A third trial may be added later from the same frozen corpus.
- **Scoring rule for names:** names are scored exactly and the scorer strips no rank. Every name field of the answer schemas says, in one text for both models, that the name is as the system records it, without rank or title.
- **Projection:** a scored task is taken to cost and take 3 times a development task (range 2 to 4). One trial is then about 21 dollars and 2.7 hours for Claude and about 6.7 dollars for GPT; two trials about 42 and 13 dollars, with 25 to 50 percent headroom proposed on top. Beta, Gamma and Epsilon are assumed from Alpha and Delta, not measured, and the dev set underrepresents the harder scored tasks.
- **Caching:** OpenAI caches repeated prefixes by itself; the Anthropic client marks the last block of each request, with a five-minute lifetime. Runs of one scenario share the system prompt and tool list, so a run can start on a cache warmed by the run before it. Cache-hit share is reported beside latency, and the timing baseline counts only runs made after the caching and request timing changes.

## Tests and the study gate

The provenance tests use a fake Docker (`fakes.py`) and never start, stop or inspect a container.

`python -B study/harness/study_gate.py` runs the offline tests of the study: this folder, the corpus derivation check and the MCP offline tests. It needs no stack and no key. The MCP suite needs the `mcp` package, which the governance interpreter does not have, so it runs under the interpreter named by the machine-local variable `STUDY_MCP_PYTHON` and is reported as NOT RUN when there is none (`--require-mcp` makes that a failure). The convention for the other study areas: put `test_*.py` files directly in the area's folder and list the folder in `SUITES` of `study_gate.py`. The live MCP stack tests (`study/mcp/test_mcp_stack.py`) are not part of the gate.

The area accepts Python, JSON, JSON Lines, TOML, Markdown and text files.
