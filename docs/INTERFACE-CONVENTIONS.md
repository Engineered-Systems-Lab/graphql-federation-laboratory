# Interface conventions

Read at commit `48130d83d10296ef6fb2917494031b83d935e440` on 2026-10-27. This page is a dated snapshot and a non-normative reference: the documents and contracts it links own each fact and win where they differ from it, and a change to an open contract should update its row here. It changes no contract, decision or code.

It says how each interface of the laboratory carries a payload and reports a failure, in the conventions actually used rather than method by method, and how those conventions compare with the outside standards. The legacy services are varied and independent by design, so a difference from a common practice below is context and not a list of things to fix.

## The federation

The adapters and routers are summarized here; [Failure semantics](FEDERATION-DESIGN.md#failure-semantics) and [who produces the outcome](FEDERATION-DESIGN.md#who-produces-the-outcome-direction-b) own the rules.

- **The owning adapter maps one call to one outcome.** A 200 is RESOLVED; the service's own not-found (Assets 404 `ASSET_NOT_FOUND`, Missions 404 `MISSION_NOT_FOUND`, the Personnel fault `PersonnelNotFound` inside an HTTP 500) is UNRESOLVED; a connection failure, a timeout or any other 5xx is UNAVAILABLE with `SERVICE_UNAVAILABLE`; any other answer, such as Assets 404 `PATH_NOT_FOUND`, a bodyless 404 or an unusable 200, is UNAVAILABLE with `UPSTREAM_BAD_RESPONSE`. UNMAPPED and RELEASE_REFUSED come from the mapping's `mappingOutcome`, and the service is not called.
- **UNRESOLVED, UNMAPPED and RELEASE_REFUSED are data**; UNAVAILABLE is data as well and also adds one `errors` entry per failed call, as a courtesy. A refused release has the release error's entry beside it.
- **Partial results answer with HTTP 200**: one service down, and the rest of the query still answers. A null `resolution` means only that the router could not ask the owning adapter.
- **The routers need a setting to pass the code through**: Apollo `include_subgraph_errors: all: true`, Cosmo `subgraph_error_propagation.mode: pass-through`; both wait 5 seconds for one subgraph request.

## The comparison

### SOAP

SOAP 1.1 defines the Fault element with `faultcode`, `faultstring`, an optional `faultactor` and `detail`, which must be present when the Body could not be processed; its standard fault codes are VersionMismatch, MustUnderstand, Client (the message was wrong and should not be resent unchanged) and Server (a processing failure that may succeed later). Its HTTP binding requires HTTP 500 for a response that carries a fault. Both Personnel services follow this: every declared fault, a not-found included, is HTTP 500, Client or Server is chosen by whose fault it is, and the application's own code and field live in `detail`. The not-found therefore cannot be read from the HTTP status, as it can in the REST services, and the Personnel adapter reads it from the fault detail.

### HTTP status codes

RFC 9110 gives the meanings the REST services use: 400 for a client error, 404 when no representation is found (saying nothing about whether that is permanent), 405 with a required `Allow` header, 406 when no acceptable representation exists, 409 for a conflict with the resource's state, 412 for a false precondition, 415 for an unsupported content format, 422 for well-formed content that cannot be processed, 500 for an unexpected condition, 503 for a temporary inability to handle the request, likely to be alleviated after some delay, and 504 for an upstream that did not answer in time. 428 comes from RFC 6585 (the server requires a conditional request). Missions and Assets use these codes in their RFC meanings and send `Allow` with 405. Two choices sit beside the standard on purpose: neither service answers 503, because a database failure is mapped to 500 (for Missions the earlier 503 mapping was superseded, see [the Missions errors](MISSIONS-V1-DESIGN.md#errors)), and Missions sends 406 with no body, where RFC 9110 suggests that the server list the representations it has.

Why an outage is not a 404 in the federation: a 404 says the thing was not found, which is the UNRESOLVED case, while an outage means it is not known whether the thing exists; the usual HTTP meaning of that is 503. The federation therefore names the outage code `SERVICE_UNAVAILABLE` after 503, as a label in `extensions` and not as a status on the wire.

### Error bodies and RFC 9457

RFC 9457 (July 2023, Standards Track, obsoleting RFC 7807) defines problem details: a JSON object with `type` (a URI that identifies the problem type, `about:blank` when absent), `title`, `status`, `detail` and `instance`, extension members that clients ignore when unknown, the media type `application/problem+json`, and an XML form `application/problem+xml` in its Appendix B. It is optional: it says that applications may use their own or domain-specific formats, and that problem details are not a debugging tool.

The Missions and Assets bodies follow the same idea, a stable machine-readable code beside the status and a human message that is not parsed, but they are not RFC 9457: the code is a plain string and not a type URI, there is no `title`, `status` or `instance`, and the media types are the plain `application/xml` and `application/json`. The sources read show RFC 9457 as a standard that a service may adopt, not as a universal practice.

**Open question, stated and not answered:** whether a later minor of an open REST contract should follow RFC 9457. The Missions contracts and Assets contract 1.0 are frozen; Assets contract 1.1 is open. It would be a decision of its own.

### GraphQL

The GraphQL specification (September 2025 edition) defines an error entry with `message`, `locations`, `path` and an `extensions` map that is reserved for implementers, and asks services not to add other keys to the entry. It defines no error codes and says nothing about HTTP. A field error makes the field null, the null propagates to the nearest nullable parent, and partial data comes back together with the errors. The lab's entries follow this: the code is in `extensions.code`, and a nullable `resolution` keeps the rest of a mission when an adapter is down. `BAD_USER_INPUT` and `INTERNAL_SERVER_ERROR` are among the built-in codes that Apollo Server documents; the other codes are the lab's own.

**Errors as data.** The 2026-10-15 material said that data-style errors are "the modern recommendation for expected failures". The sources read do not support "modern" or a consensus, so the claim is softened here. The graphql.org guide on error handling puts business and domain errors in the schema as typed data and infrastructure failures in the `errors` list, and presents the two as complementary. Apollo's guide recommends errors in the schema when they matter to the end user and keeps the `errors` list for system errors, and calls this one pattern among others. The specification takes no position. The lab's not-found, no-mapping and refused-release outcomes are data in that sense. Its outage is a system failure that the lab reports in both places, as a resolution value and as an `errors` entry, by the decisions in [Failure semantics](FEDERATION-DESIGN.md#failure-semantics).

### GraphQL over HTTP

The GraphQL over HTTP specification is a working draft, not a released standard. The current draft, read on 2026-10-27, requires servers to support the response media type `application/graphql-response+json`; for that type a response with data uses a 2xx status, a response with data and errors should use the unregistered status 294 (Partial Success, which a client that does not know it treats as 200), and a request error with no data uses 4xx or 5xx, for example 400 for an unparsable document and 422 for a validation failure. A client that accepts only `application/json` is answered as if it had asked for the new type, with `Content-Type: application/json` on a 2xx. The draft's own example of field errors during execution still answers 200.

The lab's routers answer a partial result with HTTP 200, which is the long-standing practice and what the draft's example shows. The response media type the routers send was not recorded by the lab. A request that names no release fails validation: Apollo answers HTTP 400, which matches Apollo Server's documented status for a request that cannot be validated, and Cosmo answers HTTP 200. Neither matches the draft's 422.

### The routers' own documentation

Apollo's documentation of subgraph error inclusion, read on 2026-10-27, says the router redacts subgraph errors by default (the message becomes "Subgraph errors redacted") and that `include_subgraph_errors` with `all: true` passes their messages and extensions, with a `service` extension that names the subgraph. That is the setting in the committed [router configuration](../federation/routers/apollo/router.yaml). The `GATEWAY_TIMEOUT` and `SUBREQUEST_HTTP_ERROR` entries are recorded by the lab as observed in its runs; the router's error reference read on the same day did not confirm them by name for subgraph fetches.

Cosmo's router configuration documentation, read on 2026-10-27, gives `subgraph_error_propagation` the modes `wrapped` (the default, which hides the subgraph's internals) and `pass-through` (the subgraph's error as it is), with `code` among the extension fields allowed by default. The same page lists an `enabled` key whose default is false; the lab's [configuration](../federation/routers/cosmo/config.yaml) sets only the mode, and the Cosmo README records that the code reached the client on the pinned router 0.359.0. Whether the current documentation describes that pinned version was not checked.
