## Summary

The lab composes its legacy services into one GraphQL graph with Apollo first. The subgraphs follow the Federation specification and use no vendor-specific feature, so the same subgraphs can later run under Cosmo and Hive. Each legacy system is one subgraph through a Java 21 adapter built with Spring, Maven and Apollo's federation-jvm, and a fourth Spring adapter serves the mapping releases from files. The adapters share a library. The mapping subgraph turns the Missions-local references into Personnel v2 and Assets identifiers, and every request names the mapping release it uses. A reference is shown with one of five outcomes, RESOLVED, UNRESOLVED, UNAVAILABLE, UNMAPPED or RELEASE_REFUSED, and is never hidden or guessed; the owning adapter produces the whole outcome in one call, from the mapping's explicit `mappingOutcome`. Six federation questions and their expected answers form the baseline workload.

Built and landed: the parent build and the shared library, the four adapters, the Apollo router with the committed supergraph, the Cosmo router with its committed execution config, the whole-stack compose with a stub of the Missions service, the crew mapping with the migration of the cast into Personnel v2 and mapping release 1.1, the acceptance tests, which Apollo and Cosmo both pass ([what is built](#what-is-built)), and, since 2026-10-18, the data scale-up: 1,000 people in Personnel v2, 300 missions in Missions releases 1.1 and 1.2, mapping releases 1.2 and 1.3 and a Personnel adapter that caches its snapshot, with the whole stack running on the large data ([the scale-up](#the-data-scale-up)). Each is described in its own README and is not repeated here. The Missions adapter, and not the whole stack, ran once against the real Missions service on Oracle ([the Oracle run](#the-missions-adapter-on-the-real-oracle-service)). The Hive router was not run.

Two throwaway experiments (2026-10-15 and 2026-10-16) found that the chosen library builds and runs on Java 21, that the three-subgraph chain composes with only `@key`, `@requires` and `@external` under Apollo, Cosmo and Hive, that all four outcomes then in use reached the client as data under all three routers, and that each router needs its own setting to pass the outage code through. The builds of 2026-10-16 and 2026-10-17 then settled, under Apollo, how a refused release, a dead adapter and a dead backend look to the client, and the Cosmo build of 2026-10-18 ran the same shared acceptance suite and showed the same for Cosmo ([the Cosmo router](#the-cosmo-router-of-2026-10-18)). The compatibility matrix is partly filled, and the large data added three rows to it ([what the large data found](#what-the-large-data-found)).

Still open: the rest of the compatibility matrix for Hive and the unfilled rows for Cosmo, whether a participant (P) is resolved in the graph, whether to move to newer releases of federation-jvm and Spring Boot, the machine limits, and a few details of failure semantics. The [open list](#the-open-list) names them all.

## Purpose and hypothesis

This is Phase 2 of [Plan](PLAN.md#phases-and-acceptance-gates), the reference graph: shared subgraphs and one initial platform adapter. The gate is that the schema composes and all baseline acceptance tests pass from a clean fixture reset. Phase 3 then adds the Apollo, Cosmo and Hive adapters and a repeatable harness. The plan leaves the federation semantics, the compatibility matrix, the initial platform, the exact versions, the libraries, the deployment modes and the adapter details undecided; this document records how far the design talk, the experiments and the builds have settled them.

The hypothesis the Assets design states carries over: the federation layer can compose differently built services (SOAP Personnel, XML REST Missions, JSON REST Assets) into one GraphQL view, and it behaves predictably when a reference does not resolve. Agent outcomes stay separate from router benchmarks ([D011](../project-governance/DECISIONS.md)); [Integration notes](INTEGRATION-NOTES.md#stage-a-benchmark-design) already records that vendor claims are kept apart from lab results.

## The decided principle

**The subgraphs are platform-neutral: written to the Federation specification, with no vendor-specific feature and no Apollo connectors. The platform adapter is only the router, its composition step and its deployment.** The lead developer agreed to this in the talk.

Why. The adapters that turn each legacy system into a subgraph are then written once for all platforms, which saves time, and the Phase 3 comparison is fair: the same subgraphs run under every router, so a difference is the router's. The consequence for the design is to use the fewest Federation features that do the job and to test each one on every platform, because composition tools can disagree on corner cases. That is why the [compatibility matrix](#the-compatibility-matrix) (for each Federation feature in use, which platforms accept it) is itself a deliverable.

## The platform

**Apollo is the first platform.** It provides the first adapter: the router, the composition step and the deployment. Cosmo and Hive follow in Phase 3 under the same subgraphs, so choosing Apollo first does not lock the subgraphs to Apollo, and the choice is reversible.

The lead developer's reason, with their hedge kept: their search seemed to show more demand for Apollo in the US than for Cosmo. It is a career and market-relevance criterion and a learning goal of the lab. The demand claim was not verified: it is the lead developer's reason, not a measured fact. Their wider reason for looking at Cosmo was that Cosmo can use some parts of Apollo and seemed, with those same parts, possibly to give better performance, which would be very interesting and save time if it held. Two things in it are not verified. Which parts of Apollo Cosmo can use (the Federation specification, the composition, the subgraph libraries) is their finding from a web search and is to be confirmed in the design. Whether Cosmo performs better is an **open hypothesis**, which the benchmark exists to test on this machine and these queries; it is not a fact of this document. The experiments and the builds are not that test: their figures are informal.

**The Apollo terms as read** (the texts were read on 2026-10-15; this is not legal advice):

- The Apollo router is under the Elastic License 2.0 (ELv2) by default: source-available, not open source in the OSI sense. ELv2 allows use, copying, distribution and derivative works, with three limits: no providing the software to third parties as a hosted or managed service, no circumventing the license key functionality, and no removing licensing notices. A violation ends the licences, with a path to reinstatement. A local lab that runs the router for its own benchmarks is within the terms as read; no clause about publishing benchmark results was seen in the text fetched, and the full text is to be verified before results are published.
- The subgraph library is MIT and the composition library is ELv2.
- Some router features need a licensed GraphOS plan: subscriptions, query batching, JWT authentication, field- and type-level authorization, Redis-backed query-plan caching, persisted queries and response caching, external coprocessing, request limits, demand control and safelisting, and custom instrumentation. The baseline read-only queries of Phase 2 need none of them. Field-level authorization may matter in Phase 5 (MCP and AI agents); either an offline licence, authorization elsewhere, or a comparison with Cosmo and Hive would answer it, and that is a question for the compatibility matrix, not for now.
- **FOUND:** the plain Apollo router ran with no Apollo account, graph key or graph reference, in both experiments and in the build. ## The subgraphs and their adapters

**One subgraph per system**, each through an adapter that turns the system's native contract into a subgraph: Personnel v2 (SOAP), Missions (XML over REST) and Assets (JSON over REST), plus the [mapping subgraph](#shared-identity). The legacy systems stay independent and unaware of GraphQL, as the Prime Directive requires, and the adapters are the new graph layer: they are not legacy systems. All four are built ([what is built](#what-is-built)).

**Four adapters, all Java 21 with Spring and Maven:** the three system adapters (Personnel v2, Missions, Assets) and the mapping subgraph as a fourth Spring adapter that serves the mapping releases (MAJOR.MINOR, immutable, with a checked-against list) from files. One toolchain, with the Missions packaging precedent. The lead developer agreed to this in the talk of 2026-10-15.

**The adapters share a library**, the Maven module `federation/common` (the resolution outcome, the errors-list entries and the extensions codes), under one parent pom. Legacy independence still applies between the legacy systems themselves, and the library carries no platform-specific (vendor) feature, so the subgraphs stay platform-neutral. The shape was open in the first version of this document and was settled by the layout of [D041](../project-governance/DECISIONS.md#d041---federation-graph-design-release-key-paging-names-codes-ports-and-layout-2026-10-16-accepted-scope) and the first build.

**Java with Spring.** The lead developer's reason is the résumé and the job market: Spring belongs on the résumé, a clear choice, and they said their own job-search reports show Spring mentioned everywhere. Those reports were not opened, so the claim is the lead developer's. The decision [D016](../project-governance/DECISIONS.md#d016---crew--personnel-java-soap-service-v1-2026-09-30-accepted) forbids Spring only for the standalone Personnel SOAP service, which is meant to look like a believable traditional integration; it is not a repository-wide rule and does not bind the federation layer. The adapters are Spring Boot with Spring for GraphQL.

**federation-jvm** (Apollo's `federation-graphql-java-support`, MIT) on graphql-java, inside Spring. The lead developer's decision carries their hedge: they thought federation-jvm, again because familiarity with the Apollo family goes on their résumé. The fallback is Netflix DGS (Java and Spring based); that DGS has Federation support is believed and is not verified, and neither the experiments nor the builds needed it. TypeScript with `@apollo/subgraph` was removed from the options: the lead developer judged it baggage they would find hard to defend as solid experience. What is lost is an independent JavaScript implementation as a cross-check; if a behavior question ever needs a second implementation, a throwaway experiment outside the lab can be run and discarded.

## Shared identity

The identifiers differ by system on purpose: Personnel v1 uses CRW-nnnn, Personnel v2 uses PRS-nnnn, Missions keeps its own references (crew C-n, participants P-n and O-n, assets in its own grammar such as SH-17, EQ-64 and VS-31), and Assets now has its own.

- **Assets gets native identifiers**, AST-nnnn, following the Personnel precedent of a system prefix and a zero-padded number; the grammar allows an underscore in the prefix for the future. **Missions stays exactly as it is:** its immutable release keeps its Missions-local references. The [Assets design](ASSETS-V1-DESIGN.md#contract-11-native-identifiers-and-path_not_found) owns the grammar and the controlled cases.
- **Two mappings** therefore exist in the integration layer, owned there by [D015](../project-governance/DECISIONS.md) and [D034](../project-governance/DECISIONS.md#d034---missions-v1-residual-wire-precision-2026-10-06-accepted-scope): crew, from the Missions-local C-n to PRS-nnnn (Personnel v2); and assets, from the Missions-local asset reference to AST-nnnn. Missing, ambiguous or dangling outcomes are never guessed. How the crew mapping is built is in [the crew mapping](#the-crew-mapping).
- **One federated Personnel type**, owned by Personnel v2 and keyed by `personnelId` (PRS-nnnn); Personnel v1 (CRW-nnnn) is out of the graph for now. The talk first named the type CrewMember; [D041](../project-governance/DECISIONS.md#d041---federation-graph-design-release-key-paging-names-codes-ports-and-layout-2026-10-16-accepted-scope) replaced the name and the shape, see [paging, names and the Personnel type](#paging-names-and-the-personnel-type). The exclusion of Personnel v1 from the graph was put to the lead developer as the real decision of the first topic, and their reply, which accepted the other points of that topic, did not single it out. It is therefore the reading of that reply, not a separate answer of theirs, and it can still change.
- **A mapping subgraph of its own**, taking the mapping release as an explicit argument; it is the fourth Spring adapter and serves the releases from files.
- **The mapping data is a MAJOR.MINOR release and is immutable.** A MINOR adds mapping entries, a section or controlled cases only; a MAJOR changes what an existing reference maps to, or the shape of the mapping; a published release never changes, and a correction is a new version. The release is an explicit GraphQL argument of the field that returns the references (for example `Mission.assets(release: "1.0")`), which every router and composition tool handles the same way without platform configuration. A header or a router context would need configuration per platform, which was not checked and would break the platform-neutral principle. By D015 there is no implicit latest: a request that names no release is refused, never guessed.
- **The release also travels inside the key of the reference (row 42).** Experiment 2 found that `@requires` takes a field set with no place for a variable of the client's query, so the release is a key field of the reference type (`localRef release`) as well as the argument of the field that returns the references. The experiment recorded this as a refinement of the decided form; the lead developer was asked on 2026-10-16 and accepted point 1, then points 2 to 4 together, which confirmed it as the decided form ([D041](../project-governance/DECISIONS.md#d041---federation-graph-design-release-key-paging-names-codes-ports-and-layout-2026-10-16-accepted-scope)). The no-implicit-latest rule stands.
- **The mapping version and the system version are independent.** The lead developer's first thought was to match them; they then ruled that the two change independently. The link is a record, not a number: each mapping release carries a **checked-against list** in its manifest (the system versions and dataset releases it was built for), as the Assets dataset manifest already holds the hashes of what it was checked against. A new system version that changes ids or keys gets a new mapping release; one that does not leaves the mapping alone. The mapping's own test fails when run against a system version it was not checked against, so the probable need for a new mapping is surfaced, not remembered.
- **The mapping data has controlled cases with written expected outcomes** before any code, and **participants P-n and O-n are references only**: no service owns them, so they have no rank. *Later context (2026-10-19):* this was the reading of the talk of 2026-10-15, which took P and O as participants of a mission that no service knows. The lead developer then defined what the classes mean, and a P is a person of the Personnel roster who is not crew, so a mapping release resolves it; see [the reference classes](#the-missions-reference-classes-and-their-mapping). An O is still a reference only.

## The crew mapping

Decided in the talk of 2026-10-16 ([D042](../project-governance/DECISIONS.md#d042---federation-crew-mapping-and-mapping-release-11-2026-10-16-accepted-scope)) and built. The README [Federation crew mapping](../federation/personnel-mapping/README.md) owns the process, the tables and the commands; this section says what was decided and why it was needed.

- **The problem.** Missions refers to crew by opaque C-n references and holds no names; its recipe holds the list of names to references. The Personnel v2 snapshots held seven people, of whom only a few matched the recipe names exactly. The main cast had been added to the legacy Crew and Personnel system (v1), not to v2, so a mapping to v2 needed a migration.
- **The recipe is the source of truth for the mission side.** The lead developer ruled that, for the migration, the recipe is the source of truth for the mission side.
- **The resolution process, in the lead developer's order, in four steps.** (1) The mapping exceptions table (a mission reference to a Personnel v2 id): a match stops the process. (2) A Personnel v2 record with the matching name: found, stop. (3) A matching name in Personnel v1: that person must be migrated to v2. (4) Otherwise fail and report. More than one match is a failure that reports every match and is never a pick. The same process builds the mapping live (step 3 is never run, and an unplaced reference is UNMAPPED) or as a static table for the release (an unplaced reference fails the build and prints the report).
- **Two exceptions tables.** The mapping exceptions table never names v1, and its targets must exist in v2 (otherwise a migration has to happen, which is a different thing, as the lead developer put it). A separate migration exceptions table (a mission reference to a v1 id) is used for migration only, when a name does not match in v1. After a migration a step-1 exception is added with the migrated v2 id. Both live with the process in `federation/personnel-mapping`, the lead developer's choice of name, keeping the Personnel v2 convention; the mapping exceptions reach the containers through the release, and the migration table and the script do not ship.
- **The migration.** Existing v2 ids are kept. A person migrated from v1 keeps the number of the v1 id (CRW-1048 becomes PRS-1048); the number ranges do not collide. Only the people the process marks are migrated, and the output is a new snapshot, `personnel-v2-small-003`, beside the two released ones.
- **The clearance of migrated records** (v1 has none, v2 requires one) is by rank: CAPTAIN TOP_SECRET; COMMANDER and LIEUTENANT_COMMANDER SECRET; every rank below NONE; and department SECURITY at least SECRET. The lead developer's rulings: clearance is by rank, as proposed, with every security officer at SECRET whatever the rank; then, correcting the reading that this lowers a security captain, SECRET as the minimum for security officers. The security rule is therefore a minimum.
- **Release 1.1.** `assets.json` and `crew.json` sit under one manifest in mapping release 1.1, a MINOR; 1.0 stays untouched. The lead developer proposed more descriptive file names; the finding was that a rename could only appear in a new release and arguably is a change of shape, a MAJOR. Their ruling: avoid a 2.0 for the names alone. The names stay, and `crew.json` holds the full resulting table of the crew section. A rename can be reconsidered at a future MAJOR for other reasons.
- **What the migration changed in the graph.** With release 1.0 every crew reference is NO_ENTRY and UNMAPPED; with release 1.1 all 56 crew references of the Missions dataset are MAPPED and RESOLVED against the migrated snapshot. At the time of this entry question 6 was thought to need the Personnel live path; later it was found that this crew path is that live path, so question 6 needed no new adapter code and is answered and tested under Apollo.

## Paging, names and the Personnel type

Decided on 2026-10-16 ([D041](../project-governance/DECISIONS.md#d041---federation-graph-design-release-key-paging-names-codes-ports-and-layout-2026-10-16-accepted-scope)); the adapters implement it.

- **Paging at the graph level is offset and limit.** The default is 20 and the maximum is 100; the lead developer set the maximum at 100, just in case. Personnel v2 allows 100 per call and Missions and Assets allow 50, so a page above 50 takes two calls to those two services, and the Missions adapter translates offset and limit into its page and page size. Relay-style cursor connections were considered and not chosen, because the backing services are offset-based and cursors would be synthetic. A limit above 100 is a `BAD_USER_INPUT` error.
- **A page is all or nothing.** If any backing call of a page fails, the whole list is null with one SERVICE_UNAVAILABLE entry: a list is either complete or absent and never silently short. The lead developer ruled all or nothing. There is therefore no PARTIAL_RESULT code; the alternative, partial pages with an error entry and the expected and returned counts, was not chosen. The Personnel page carries the dataset version of the snapshot that answered; the adapter holds no state, so the client compares it on every page and restarts at offset 0 when it changes, as the Personnel v2 contract says. No DATASET_CHANGED code was added.
- **Names are the owning system's vocabulary**, camelCase fields taken from each contract's own field names, with no renaming layer; enum names and values come straight from the contracts. The graph types are `Mission`, `Asset`, `Personnel`, the two reference types and the enums.
- **The Personnel type.** The lead developer asked for a Personnel type rather than CrewMember, and for some form of inheritance or choice like Personnel v2. The decided form (their choice of option A) is the entity `Personnel` keyed by `personnelId`, owned by Personnel v2, with the shared fields and a field `details` whose type is a union of `CrewDetails` and `CivilianDetails`. This mirrors the choice of the Personnel v2 contract and needs only `@key`. **Civilians are therefore in the graph** (they were out under the name CrewMember) and carry no rank; the participants P-n and O-n stay references only, and Personnel v1 stays out. The question 6 definition reads the rank from `details` when it is `CrewDetails`; a civilian is never senior. The rejected option was an interface `Personnel` implemented by crew and civilian types; it would need the Federation entity-interface feature (`@interfaceObject`) for references that do not know the subtype. That feature was not tested, and whether Cosmo and Hive accept it is unknown; it may be tried later as a compatibility-matrix item.
- **The exact field list of every type** was approved by the lead developer in the preview of each adapter's first build; it is in the adapter's schema and in the committed supergraph, not here.

## Failure semantics

An asset reference of a mission appears with `resolution` and `asset`, with `asset` null when it is not resolved ([Assets design](ASSETS-V1-DESIGN.md#the-federation-outcome-as-the-consumer-expects-it)); a crew reference has `resolution` and `personnel`. Each also carries its `localRef`, its `release`, the mapped id (`assetId` or `personnelId`) and the mapping's `mappingOutcome`. The decided values of `resolution`, which the talk applied to the crew and mission references as well as to assets:

| Value | Meaning |
| --- | --- |
| RESOLVED | The owning service has the thing. A DESTROYED or MISSING asset is RESOLVED with its status; the federation makes no judgment about timing. |
| UNRESOLVED | The owning service answered that the thing does not exist: for Assets only a 404 whose code is ASSET_NOT_FOUND, never PATH_NOT_FOUND or any other failure; for another service the equivalent not-found. |
| UNAVAILABLE | The owning service could not answer (a connection failure, a timeout or a 5xx), so it is not known whether the thing exists. The referenced object is null. |
| UNMAPPED | The mapping layer has no entry for the reference in the named mapping release (`mappingOutcome` NO_ENTRY, which includes a valid release that has no section for the kind of reference). It is the mapping layer's own outcome and is never reported as UNRESOLVED. |
| RELEASE_REFUSED | The mapping layer refused the release named by the request (blank or unknown). Added on 2026-10-17 ([D043](../project-governance/DECISIONS.md#d043---federation-graph-refinements-mapping-outcome-asset-id-parent-timeout-and-nullable-resolution-2026-10-17-accepted-scope)). The `MAPPING_RELEASE_REQUIRED` or `MAPPING_RELEASE_NOT_FOUND` errors entry stays beside it and says which. |

The talk reached UNAVAILABLE as follows. The lead developer asked what the modern way is, and offered a 404 with UNAVAILABLE if there is none. The answer was that a 404 is the wrong status, because a 404 means the thing does not exist, which is the UNRESOLVED case, while an outage is the opposite: not knowing. GraphQL has no status code per field. The federation answers the whole query with HTTP 200 and partial data, with the failures in the errors list, and the code belongs in the error's `extensions`. Of the two accepted patterns (errors as extensions, and errors as data in the type), the lab already uses the second for not-found, and the lead developer asked for it to be recorded that way. UNMAPPED was added on 2026-10-15 as a fourth value: the lead developer accepted UNMAPPED as a fourth value with one error per call. The reason put to them, which their answer accepted, was that no mapping entry and a service that says the thing does not exist are different causes, and a client that sees them apart can tell a data gap from a mapping gap. RELEASE_REFUSED follows the same reasoning for a refused release, see [the refinements](#the-refinements-of-2026-10-17).

Decided on top of the values:

- **The outage shape applies to all services**, crew and missions as well as assets: the referenced object is null and the failure is reported, never hidden and never guessed.
- **Every failure also adds an entry to the GraphQL `errors` list** as a courtesy: a path to the field, a stable machine-readable code in `extensions` and a short message, so a client that reads only the errors list still sees it. For an outage the code is SERVICE_UNAVAILABLE, the usual meaning of HTTP 503, and not a status code on the wire. The full code list (row 45) is SERVICE_UNAVAILABLE, MAPPING_RELEASE_REQUIRED, MAPPING_RELEASE_NOT_FOUND, UPSTREAM_BAD_RESPONSE (the service answered something the adapter cannot use), BAD_USER_INPUT (a malformed argument from the client) and INTERNAL_SERVER_ERROR (an adapter fault). **UNMAPPED, UNRESOLVED and RELEASE_REFUSED are data**; UNMAPPED and UNRESOLVED add no entry, and RELEASE_REFUSED has the entry of the release error beside it. The talk named the last two codes as Apollo Server's documented ones, recalled and not verified at the time; the shared library records that they were checked on 2026-10-16.
- **One entry per failed call, not per failed reference.** A call to a service that fails once yields one entry, however many references depended on that call; every reference that depended on it still shows UNAVAILABLE with a null object. In the built stack the router asks the adapter once per reference occurrence and does not merge identical calls, so a list with 65 mapped references and the Assets service down made 65 entries, one per call. The decision is per call.
- **Partial results:** one service down, and the rest of the query still answers, with HTTP 200.
- **The controlled cases of the [Assets dataset](ASSETS-V1-DESIGN.md#the-federation-outcome-as-the-consumer-expects-it)** (and the Missions dataset) are the acceptance tests, with their expected outcomes written before any code.

### Who produces the outcome (direction B)

**Decided as the direction (2026-10-16):** the owning adapter produces the whole outcome in one call. The finding that raised the question was that a router returns an entity or null and does not produce a resolution value (see [what the experiments found](#what-the-experiments-found)), so one of the lab's own adapters must produce it. Three ways were put to the lead developer: the mapping subgraph probes the owning service (two asks of the same fact, which can disagree), the owning adapter produces the whole outcome in one call, or the Missions adapter calls the services itself (a gateway of its own, ruled out). They chose B as the direction.

The owning adapter (Assets for assets, Personnel v2 for crew) owns a reference type, for assets `AssetReference`, which the router asks it for through `_entities`, once per reference. The adapter calls its service once and derives the whole outcome: a 200 gives RESOLVED, a 404 with the code ASSET_NOT_FOUND (or the equivalent not-found of another service) gives UNRESOLVED, and a failure of the service gives UNAVAILABLE with one errors-list entry per failed call whose `extensions.code` is SERVICE_UNAVAILABLE. One call produces the value and the object, so they cannot disagree. The mapping subgraph supplies the mapped id and the mapping outcome; the owning adapter no longer infers the cause from a null id ([the refinements](#the-refinements-of-2026-10-17)). The same pattern holds for crew with the Personnel v2 adapter, so every service behaves alike. The Missions adapter calls neither the mapping nor the services: it supplies reference stubs whose keys are not resolvable by it.

The direction was decided with three costs recorded:

1. **A Federation feature beyond `@key`.** The owning adapter needs the mapped id that another subgraph computes, which in Federation means `@requires` with `@external`. If a platform did not accept it, the direction would be reconsidered. **FOUND:** all three routers accepted it ([found by the experiments](#what-the-experiments-found)).
2. **A limit, DECIDED with the direction:** if an adapter itself is down, the router reports it and the lab cannot turn that into UNAVAILABLE as data. Only the failure of the service behind a running adapter becomes UNAVAILABLE; the router-level failure shows as the router's own error. The first build measured how it looks: see [the refinements](#the-refinements-of-2026-10-17), which also say how much of the answer survives.
3. **Router configuration.** The default router hides subgraph errors, and a router setting passes them through. **FOUND:** each router has its own setting and with it the client receives the code ([found by the experiments](#what-the-experiments-found)). The Apollo setting is in the committed router configuration.

Open in failure semantics:

- **Whether the entry's `extensions` lists the paths of the affected references, or their count,** so a client that reads only the errors list can see the extent. It was proposed and not decided.
- **Queries that omit `resolution` and `asset`:** the experiment attached the error to the first resolved field of the entity, so such a query gets no entry. The router build tested seven selection shapes and found that a reference is always listed and equals the expected outcome ([row 60](#what-the-builds-found)). The lead developer asked for the test; they have not ruled on whether a query that never asks for the outcome getting no entry is acceptable.
- **Per-entity errors:** the Assets entity reports its errors at the `_entities` path without a per-entity path, because the error is attached to a field of the entity. Whether federation-jvm can return a per-entity error from its entity fetcher itself was not tested.
- **Nullable fields and partial results on Cosmo and Hive** beyond the shape tried (see row 29 and the [compatibility matrix](#the-compatibility-matrix)).

## The refinements of 2026-10-17

The first end-to-end run of the Apollo router raised four findings; the lead developer ruled on each on 2026-10-17, and one more ruling followed the same day ([D043](../project-governance/DECISIONS.md#d043---federation-graph-refinements-mapping-outcome-asset-id-parent-timeout-and-nullable-resolution-2026-10-17-accepted-scope)). All five are built. The evidence is in [the Apollo router README](../federation/routers/apollo/README.md) and in the findings sections of [Integration notes](INTEGRATION-NOTES.md#federation-graph-refinements-findings-of-2026-10-17-apollo-router-v2180).

- **A refused release as data (rows 53 and 54).** The finding: a blank or unknown release was refused by the mapping subgraph (a null entity and one release-error entry per reference), the owning adapters then saw a null id and derived UNMAPPED, so a client reading only the data could not tell a refused release from a reference with no entry in a valid release. The lead developer chose a fifth resolution value (option B), for a clean design and implementation with fewer guesses. The design: the mapping states its outcome in an explicit field `mappingOutcome` (one enum `MappingOutcome` with MAPPED, NO_ENTRY and RELEASE_REFUSED, for both kinds of reference), and the owning adapters read the mapped id and the outcome through `@requires` instead of inferring the cause. NO_ENTRY gives UNMAPPED, RELEASE_REFUSED gives RELEASE_REFUSED, and MAPPED is looked up. The lead developer accepted both names, `RELEASE_REFUSED` and `mappingOutcome`, as clear. The errors entries `MAPPING_RELEASE_REQUIRED` and `MAPPING_RELEASE_NOT_FOUND` stay. The Missions adapter does not change, because it never calls the mapping.
- **The asset id is `assetId`, and the redundant `id` is gone.** On the name, the lead developer judged `astId` a poor choice and chose `assetId`. The reference types had an `id` field that was a vestige of the first direction-B shape, where it was the key, and that duplicated the mapped id and `asset.assetId`. The lead developer's concern was whether the duplication could introduce uncertainty into the design, and they asked for it to be explored; after the exploration they asked for the design to be recorded. The reference types no longer have it. The earlier records that say `astId` stay as written (Historical Truth).
- **`Asset.parent` (row 55).** The finding: `Asset` had a `parentAssetId` and no parent object, so the parent chain of question 4 took one query per level. The lead developer chose to add a `parent` field (option A), to get as much value out of the graphs as possible. The Assets adapter resolves it itself from its own service, so it is an in-subgraph traversal and a Federation feature is not needed; it is lazy, so a call happens only when the client selects `parent`, and each level is one call. A failed call gives `parent` null with one SERVICE_UNAVAILABLE entry; a parent id that does not exist gives null with no entry (proposed in the preview and not objected to). There is no caching and no batching: the lead developer believes batching is not implemented in the legacy Assets service, and ruled that caching is left for a later improvement, when and if the need becomes apparent. A rule for traversals was offered (add one when a baseline or demo question needs it, the owning system's data holds the link, and the honest-result rules hold) and was not confirmed. Question 4 is now one query.
- **A dead adapter and the 5 second timeout (row 56).** The finding: when an adapter itself is down the router answered HTTP 504 after 30 seconds, its default, with `data` null. The lead developer's ruling was to use partial data for the dead subgraph if Apollo supports it cleanly, otherwise a shorter timeout (option B if Apollo supports it cleanly, otherwise option A). Apollo has no such setting (row 58), so the router waits 5 seconds for one subgraph request (`traffic_shaping.all.timeout: 5s`): about four times the slowest normal answer measured, 1.3 seconds for a whole-list query. The lead developer accepted the value. They wanted the timeout as an environment variable at some point and then said it is not planned: it will be added if and when it is needed. The timeout stays fixed in `router.yaml` until tests on the Apollo federation show a need.
- **A nullable `resolution` (row 57).** With the 5 second timeout and a non-null `resolution`, the router answered HTTP 200 but `data.mission` was null, because the null climbs to the nearest nullable parent. The lead developer, on making `resolution` nullable, read it as letting a dead subgraph keep the rest of the mission, which sounded good to them, and asked whether that reading was right; after the trade-off was explained, they decided to do it. Decided: `resolution` is nullable on both reference types (`asset` and `personnel` already were). **A null `resolution` means only that the router could not ask the owning adapter** (the adapter is down, or the mapping subgraph that supplies its `@requires` input is), and the errors entry (GATEWAY_TIMEOUT, with `extensions.service` naming the subgraph) says why. Every other case is an explicit value as data, and the adapters never return a null `resolution`. The price is that the schema no longer guarantees that `resolution` is present: a client must check the errors list whenever it is null, and must not read a null as UNRESOLVED or UNMAPPED, which have values of their own. The gain is that a dead subgraph costs the fields it owns and not the mission or the whole list.
- **What the router Job did not test, and the lead developer's answers.** The real Missions service on Oracle: the lead developer would run it later themselves (about 9 GB, minutes to start). *Later context (2026-10-19):* the Missions adapter alone ran once against the real service, and the lead developer chose the adapter stage only ([the Oracle run](#the-missions-adapter-on-the-real-oracle-service)). Queries that omit `resolution` and `asset`: tested in the same Job. The `@requires` set with an argument, entity interfaces, the Hive Console, Cosmo and Hive: left for the later Cosmo and Hive build, which owns the compatibility matrix. At the time the live crew path was expected to belong to a Personnel follow-up (question 6); later the crew path of release 1.1 served it, and question 6 is answered and tested under Apollo.
- **The profile text.** The limits text of the federation check profile still said every crew reference stays UNMAPPED after release 1.1. The lead developer ordered it updated, and it was corrected with the nullable-resolution change, under the sealed Approve.

## The Missions reference classes and their mapping

Decided on 2026-10-18 and 2026-10-19 ([D045](../project-governance/DECISIONS.md#d045---missions-dataset-release-12-participants-reclassified-as-p-and-o-2026-10-19-accepted-scope) for the classes and the data, [D048](../project-governance/DECISIONS.md#d048---federation-mapping-of-the-missions-reference-classes-o-refused-by-class-and-p-to-non-crew-personnel-2026-10-19-accepted-scope) for their mapping) and built in the data and in the mapping releases. The [Missions design](MISSIONS-V1-DESIGN.md) owns the definitions and the data rules; [the crew mapping README](../federation/personnel-mapping/README.md) owns the process and its commands; this section says what the federation does with them.

- **The meaning.** The Missions-local references keep their grammar and have three classes. **C** is crew: Starfleet crew members, assigned with obligations. **P** is Personnel: people on the Enterprise who work or live there and are not crew members, the civilians of the Personnel v2 roster; a P reference is expected to map to a PRS identifier. **O** is Outsiders, the Others: anyone not on the ship's roster, of any kind, and an O reference never maps. The lead developer's ruling (2026-10-19): P was meant to be Personnel, the people on the Enterprise who work there and are not crew members, which they had thought was clear; calling the Tau Cygna V colonists P-237 and P-250 while describing them as outsiders is wrong, and they should have been O; O is not for groups and objects but for Outsiders, the Others; and the word entity is used because Star Trek has all sorts of creatures, humanoids and other entities, so it is the broad classification that fits all.
- **FOUND: the data had drifted from the meaning.** Missions release 1.0 used P for outsiders (the Tau Cygna V colonists), and the generator of release 1.1 continued it: 118 distinct P references with 295 occurrences, of which only two resolve to the roster, and about 100 of them were placeholders; O had been used for groups and objects. The lead developer chose clean data (option A): a new Missions release reclassifies the participants and keeps every identity of release 1.1 (Missions release 1.2, D045). Releases 1.0 and 1.1 keep their classification as history.
- **The identity trap.** The returning Wesley Crusher (a visitor of two Season 5 missions, a cadet) is the same human as a crew member of the roster, PRS-0714. The lead developer's ruling at the build of Missions release 1.1: P is for Personnel, and when Wesley returns to the Enterprise he is not part of the crew but an outsider, entity because an outsider could be anything, a human included. He is therefore an O reference (O-860), and a mapping that matched by name would have linked an outsider to a crew identity.
- **O is refused by class (D048).** The crew mapping process decides the class of a reference before it reads a name. It never accepts an O reference, whatever its name, and no exceptions table can name one. The lead developer's ruling (2026-10-18): record that O references are refused by class in the scale-up design record of that Job, and allow P. The rule is structural and not a per-person exception, so every outsider who shares a name with someone on the roster is protected.
- **P is allowed (D048).** A P reference maps only to a non-crew person of the roster, by the participant exceptions table (which wins) or by an exact name. More than one match is a failure that reports every match, and a name that only a crew member holds is a failure and not UNMAPPED (the lead developer agreed to point f.1). The table holds one entry, P-1003 (Alexander) to PRS-3001, which the lead developer chose in a dialog.
- **How the mapping releases implement it.** Release 1.2 (2026-10-19) maps the 800 crew references of Missions release 1.1 (794 by name and six by the crew exceptions table, with the ten entries of mapping release 1.1 unchanged) and the two participants of that release that resolve (Guinan, P-1068, to PRS-0003 by name, and P-1003), and refuses its 28 O references by class; three crew references that the Missions recipe lists apart as unmapped are not offered to the process and have no entry. Release 1.3 (2026-10-19) is built for Missions release 1.2 in a strict participant mode: it resolves all 58 P references (57 by exact name, P-1003 by the table) and refuses 153 O references, among them O-860 and the off-roster civilian of release 1.2, and an unplaced P is a build failure that names the reference and no longer an UNMAPPED outcome. Its crew and asset sections are those of release 1.2 byte for byte. A published release never changes, so release 1.2 keeps its looser rule.
- **OPEN: the graph does not resolve a participant.** The Missions adapter serves `participantIds` as plain data and the mapping releases carry the participants, but no field of the graph returns a resolved participant. The lead developer deferred it until the agent corpus needs it. A proposal that was not decided is to expose it, the design's own case being a participant and a later crew reference that reach one PRS identifier (Guinan's P-1068 and her crew reference both reach PRS-0003).

## The Personnel adapter cache and the warm-up

Decided on 2026-10-19 ([D049](../project-governance/DECISIONS.md#d049---federation-personnel-adapter-snapshot-cache-and-the-warm-up-of-the-acceptance-suite-2026-10-19-accepted-scope)) and built in the runtime commits lab commit `32279dc6bb407a9b8a0d8be5f6e13f5d92a015d4` (the cache) and lab commit `e68dbc0f06a1c41b31832a1a9e5b4f1193a9e025` (the warm-up). [The snapshot in memory](../federation/adapters/personnel/README.md#the-snapshot-in-memory) owns the design and [the acceptance README](../federation/acceptance/README.md#paging-the-warm-up-and-the-timeout) the suite.

- **The finding (FOUND, one machine).** When the stack first served the large data, a page of 100 missions with assets, commanding officer and crew held 750 to 1,250 references and took 5.1 to 5.6 seconds on the first pages after a start, which is the 5 second subgraph timeout (partial answers with timeout entries), and 0.8 to 3.5 seconds warm, through both routers. The main cost was the Personnel adapter making one SOAP call per person, plus cold JVMs. The worker stopped there, as its brief required, and the lead developer chose.
- **Options A and C, the 5 seconds unchanged.** The lead developer chose options A and C. (A) The shared acceptance suite warms the stack before its first assertion, because acceptance tests correctness and not cold latency, and the cold figure is reported as a finding and not hidden. (C) The Personnel adapter reads each immutable snapshot once, in pages of 100, keyed by `datasetVersion`, and answers its entity lookups from memory. Not chosen: smaller pages, which hide the problem, and higher CPU limits, which change the benchmark environment. The caching is what the ruling of 2026-10-16 on `Asset.parent` deferred until the need became apparent; the need became apparent.
- **How the cache keeps an outage an outage.** A snapshot is immutable by the Personnel v2 contract and every answer names its `datasetVersion`. Each batch (one `_entities` call) starts with one cheap list call (offset 0, limit 1), the probe, which proves the service answers now and names the version. A copy is never served without a probe that has just succeeded, so a dead service is detected once per batch and each reference in it is UNAVAILABLE with the code the failed call had before. A new version empties the copy and reads again, a version that changes between pages restarts the read, and `Query.personnel` and `Query.personnelMembers` still make one call each. The copy survives an outage. The adapter now holds state, one snapshot at a time.
- **Measured before and after (FOUND, informal).** Four rounds of three pages (offsets 0, 100 and 200) on a cold stack, on this desktop with the provisional container limits. Before, the first rounds took 5.1 to 7.7 seconds a page through both routers with timeout entries (936, 490 and 695 under Apollo, 2 a page under Cosmo), and the warm pages 1.3 to 3.8 seconds. After, none of the 24 pages carried an errors entry; the first page of a cold stack took 3.59 seconds under Cosmo and 4.19 under Apollo, the other pages 0.47 to 0.68 seconds under Cosmo and 0.46 to 0.85 under Apollo, and every page resolved the same references as the warm pages before. The stack gate saw 3.11 and 1.96 seconds for the first pages and 0.45 to 0.86 for the warm ones. These are facts of single runs and not a benchmark.
- **No read of the snapshot at adapter start (DECIDED).** It would add margin to the first page (the margin under Apollo is about 1 second) but blur the cold-start metric. The lead developer agreed not to do it (point d), to be reconsidered only if acceptance runs fail.
- **The warm-up rule in the suite.** Before its first assertion the suite asks the three heaviest pages once and keeps the cold figures as facts. After that a normal page must answer well before the subgraph timeout in force, which is the least time a dead adapter takes (4.5 seconds): a normal page that takes as long fails.

## What the large data found

These are facts of single runs of the built stack on the large data, for the compatibility matrix; they decide nothing, and the times are informal and not a benchmark. The tables are in [the Apollo router README](../federation/routers/apollo/README.md#the-large-data-2026-10-19) and [the Cosmo router README](../federation/routers/cosmo/README.md#the-large-data-2026-10-19); the lead developer ruled on 2026-10-19 to record the first two in the matrix.

- **A dead adapter on a paged list (row 83).** With an adapter stopped, the whole list of 300 missions (three pages of 100) kept every mission and gave partial data with HTTP 200 on both routers. A page could answer in about 3 seconds where the 5 second subgraph timeout would have been expected: the worker that derived the outcomes saw 3.0 second pages on both routers, and the gate runs recorded for Cosmo pages of 5.05, 3.0 and 5.05 seconds (Assets stopped) and for Apollo pages of 5.1 to 5.2 seconds. **The cause of the 3 seconds is not verified.** The suite therefore checks such a list as a list: every page inside the upper end of the declared window, and at least one page that waited for the timeout.

It is a declared per-router setting of the shared suite (`adapter_down_other_codes`, Apollo: `SUBREQUEST_HTTP_ERROR`) that applies to a list only; a single answer stays strict. The same code was seen after a restart of the adapters (row 62).
- **The first page of a cold stack (row 84).** Once the Personnel adapter has read its snapshot, the first full pages took 3.11, 0.74 and 0.49 seconds under Apollo and 1.96, 0.64 and 0.62 seconds under Cosmo in the stack gate, and, once warm, 0.86, 0.49 and 0.49 seconds under Apollo and 0.49, 0.45 and 0.63 seconds under Cosmo. Before the cache they took 5.1 to 5.6 seconds with timeout entries. The cold figure is recorded with the warm ones as a FOUND fact and not as a benchmark; the benchmark protocol distinguishes cold and warm runs.
- **Entries for a dead adapter on a list (row 85).** With the Assets adapter stopped, the 300 missions gave 596 `GATEWAY_TIMEOUT` entries under Apollo (one per reference whose owning subgraph could not be asked) and 3 under Cosmo (one per failed fetch, one per page). This is the per-reference against per-fetch difference of row 73, now on a list of 300.
- **Already in the matrix, from the Cosmo build:** Cosmo retries subgraph requests by default and the build switched that off (Apollo 2.18 has no setting); Cosmo's composition output depends on the order of the subgraphs and Rover's does not; Cosmo found restarted adapters by itself within 16.4 seconds where the Apollo router needed a restart ([the Cosmo section](#the-cosmo-router-of-2026-10-18)).

## The query workload

The talk split the workload in two, because a vague term would make the router benchmark measure the lab's guess and not the router ([D011](../project-governance/DECISIONS.md) keeps agent outcomes apart from router benchmarks).

**List A: federation questions** (router and composition tests). Each is precisely defined and has an exact expected answer written in the dataset provenance before any code. List A is the baseline set for the Phase 2 gate. The router build covers questions 2, 3, 4, 5 and 6 under Apollo and Cosmo; question 1 is not built.

1. **When was this asset last seen?** The asset's last recorded mission (mission id and stardate), labeled as a fact and never as the loss date: the last mission is not the loss, and an asset may even appear in a later mission by mistake, which is a good controlled case. Missions orders by stardate ascending and has no descending sort, so the federation reads `totalPages` and fetches the last page of the supported `assignedAssetId` filter: two requests per asset (the [ordering and filters](MISSIONS-V1-DESIGN.md#collection-filters-pagination-and-ordering) are the Missions design's). An optional status stardate in Assets was considered and not chosen.
2. **Which missions used a destroyed or missing asset?** A join across Missions and Assets filtered by the asset status.
3. **Which missions have unresolved assets?** The missions whose assigned asset references come back UNRESOLVED.
4. **The parent chain:** a mission, its assets and each asset's parent ship in one query. It is a case of the dataset, not a separate question. Since `Asset.parent` it is one query.
5. **What does a mission look like when the Assets service is down?** The mission and its other fields still answer, each asset reference has `resolution` UNAVAILABLE and a null asset, and the errors list carries one entry per failed call, as described [above](#failure-semantics). It is not the dangling case. The acceptance test stops the service in the stack; the same test also stops an adapter itself (see [the refinements](#the-refinements-of-2026-10-17)).
6. **How many missions had one or more senior officers among their Starfleet personnel, and what percentage is that?** The answer has three counts and one percentage (below; the rules are [D046](../project-governance/DECISIONS.md#d046---federation-question-6-the-people-counted-the-three-counts-and-the-status-rules-2026-10-18-accepted-scope)). A **senior officer** is a rank of CAPTAIN, COMMANDER or LIEUTENANT_COMMANDER; LIEUTENANT and ENSIGN are junior, CHIEF_PETTY_OFFICER and CREWMAN are enlisted, and civilians have no rank. **The people checked** (the lead developer, 2026-10-18, which replaces their ruling of 2026-10-15 that the commanding officer is not counted and only `assignedCrewIds` is) are the mission's Starfleet personnel: the commanding officer (`commandingOfficerId`) **plus** the assigned crew (`assignedCrewIds`); the participants (P-n, O-n) never count. Their reason: a commanding officer is assigned too, not as a member of `assignedCrewIds` but because someone assigned them to the mission or they volunteered. The commanding officer is a separate field and is never also in `assignedCrewIds` (0 of the 27 missions of the small data that have one); the contract requires it from AUTHORIZED on, and a PLANNED or CANCELLED mission may have none. The definition is the lab's, written in the dataset provenance; it is not a claim about any navy, and the naval convention that officers from lieutenant commander up are senior was recalled from memory and is not verified. The question crosses Missions, the crew mapping and Personnel v2, and the rank is the one in the Personnel v2 dataset release that the mapping release names, with no judgment about timing. Honest-result rules: a reference (of the commander or of the crew) that is UNMAPPED, UNRESOLVED, RELEASE_REFUSED or UNAVAILABLE, or whose resolution is null because the Personnel adapter cannot be asked, is never counted as senior and is never guessed; the mission is then unconfirmed unless another person is confirmed senior. **The answer shape (the lead developer, 2026-10-17, which supersedes the denominator they confirmed on 2026-10-15 and the earlier lower-bound reading).** The lead developer ruled that, to be honest, an unconfirmed mission counts neither as having a senior officer nor as not having one; the answer shows the number confirmed with a senior officer, the number confirmed without one and the number unconfirmed, and the percentage of the confirmed. The three counts, by the bucket rule that was put to them with that question (their choice of A accepted the message as a whole): **confirmed with a senior officer** is a mission with at least one of its personnel confirmed senior (the unconfirmed people of that mission do not matter, the answer is already yes); **confirmed without** is a mission whose personnel are all confirmed and none is senior; **unconfirmed** is a mission with no confirmed senior person and at least one person that cannot be confirmed. The percentage is option A, their choice: confirmed with, divided by confirmed with plus confirmed without, shown with one decimal; the unconfirmed count is shown beside it and is never folded into either side. On the rounding they chose half up, so a tie goes up. When no mission is confirmed the percentage is not a number, and the answer says so instead of printing 0. The definitions of senior and of civilians are unchanged, and the graph has no aggregate field, so the client and the test count; the graph gained one field for this, `Mission.commandingOfficer(release)`, a nullable `PersonnelReference` beside `crew(release)`, with the same mapping, outcomes and rules (`commandingOfficerId` stays). **A mission with nobody at all, the PLANNED missions and the CANCELLED missions (the lead developer, 2026-10-18).** A mission with nobody at all (no commanding officer and no assigned crew: the PLANNED missions ST-00000LD4V and ST-00000LD57) was first ruled, by their answer D, unconfirmed while PLANNED (an empty list on a planned mission means not staffed yet, not a confirmed no) and confirmed without a senior officer once it had started or ended. The first built three-count answer then showed one more case: the only confirmed-without mission, ST-00000LD5G, is PLANNED, has no commanding officer yet and one assigned member (CHIEF_PETTY_OFFICER), so it is planned and only partly staffed, and "without" was a premature no. They widened the rule, because it is consistent only if it holds that way for every PLANNED mission. **The rule now:** a PLANNED mission is unconfirmed unless it already has a confirmed senior officer (it can be confirmed with, never confirmed without, because its staffing is not final); this replaces the narrower D. The other statuses (AUTHORIZED, ACTIVE, POSTPONED, COMPLETED, FAILED) count by their staffing as above, and a mission of one of them with nobody at all is confirmed without. **CANCELLED missions are out of the population.** The lead developer was undecided about CANCELLED missions and asked what purpose it serves to know, either way, whether senior officers are assigned to cancelled missions; after the answer they agreed it matched their own thinking and asked for it to be recorded. The reason (from the answer they agreed with): question 6 asks how many missions had senior officers among their crew, a question about missions as they actually ran; a cancelled mission never ran, so its staffing describes a dropped plan, and counting it either way answers a different question. A cancelled mission is therefore in none of the three counts and not in the percentage, whatever its staffing, and the number of cancelled missions not counted is reported beside the answer (`cancelledNotCounted`), never folded into any bucket. The suite holds both rules in one place, the status test of its counting function, and the derivation in `derive_expected.py` (`EXCLUDED_STATUS`, `UNFINISHED_STATUS`). Expected answers on the small data (31 missions, Missions release 1.0), derived from the released files before the suite was changed: mapping release 1.1 with every service up: 27 confirmed with, 0 confirmed without, 3 unconfirmed (ST-00000LD4V, ST-00000LD57 and ST-00000LD5G, all PLANNED), 100.0 percent of the confirmed missions, and 1 cancelled mission not counted (ST-00000LD5D). Release 1.0 (no crew section, every reference UNMAPPED) and the Personnel adapter down: 0, 0, 30, not a number, and 1 cancelled mission not counted. The figures 28 / 0 / 2 that were given with the ruling were an estimate, to be derived again by script, and the estimate was wrong: the derivation gives 27 / 0 / 3, because ST-00000LD5G is unconfirmed as a PLANNED mission and ST-00000LD5D, now left out, was one of the 28 confirmed with. (Before these two rules the answer was 28 / 1 / 2 and 96.6 percent for release 1.1 and 0 / 0 / 31 for release 1.0 and the Personnel adapter down; with the commander left out, as first built, the counts were 25 / 6 / 0, 80.6 percent, and 0 / 4 / 27 for release 1.0 and Personnel down, the four crew-less missions then counting as confirmed without.) **On the large data** (300 missions, Missions release 1.2, mapping release 1.3, `personnel-v2-large-004`) the derivation gives 182 confirmed with a senior officer, 65 confirmed without, 26 unconfirmed, 73.7 percent of the confirmed missions and 27 cancelled missions not counted, with 12 references not resolved; Missions release 1.1 with mapping release 1.2 gave the same figures, so the reclassification of the participants changed none of them, and release 1.0 with the Personnel adapter down gives 0 / 0 / 273, not a number, and the same 27 cancelled missions not counted. Only 16 of the 800 crew are senior, which is why the small-data answer of 100.0 percent became a spread. Its acceptance test is these counts for the released datasets, computed before any federation code, with controlled cases built from small inputs: a mission with one confirmed senior and one unconfirmed member (confirmed with), a mission with only confirmed non-senior members and one unconfirmed member (unconfirmed), one case for each kind of unconfirmed member, a mission whose only senior is the commanding officer, a commanding officer that cannot be confirmed, missions with nobody at all (unconfirmed while PLANNED, confirmed without otherwise), PLANNED missions (a confirmed senior is with, only confirmed non-senior members are unconfirmed), CANCELLED missions of every staffing (left out and counted beside), each other status by its staffing, and the percentage cases (a tie, the unconfirmed in neither side, none confirmed, the cancelled missions changing nothing). The percentage over all missions, "whatever their status", decided on 2026-10-15 and recorded in the entries below, is superseded and stays there as written.

**List B: agent questions** (the Stage A evaluation, scenarios Alpha to Delta in [Plan](PLAN.md#read-only-agent-comparison-framework)). They are worded naturally, and deliberate ambiguity is part of the difficulty: question 6 in its natural form ("how many missions had senior officers among their crew, and what share is that?") does not say what "senior" means, so the agent must ask, or choose a reasonable definition and state it, or guess silently. The scoring rewards the first two and penalizes the silent guess, and the expected answer is given per accepted definition. List B is not part of Phase 2; it belongs to the evaluation design. A candidate for it, not recorded as a question, is the cost ranking by mission type, a Missions-only aggregation of the estimated and actual costs (the [cost lifecycle table](MISSIONS-V1-DESIGN.md#cost-lifecycle-invariants) says which statuses carry which cost). The lead developer dropped an outliers question.
